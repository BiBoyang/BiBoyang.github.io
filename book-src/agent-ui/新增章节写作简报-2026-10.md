### A. ch03 补记:表格 holdback 的独立收敛(含代码块盲区的"他山答案")

**动机**:ch03 §3.2 的 `retreatToAvoidSplittingTrailingStreamingTable` 是作者独立发明的防御;2026-10 读 Codex 流式渲染源码发现,Codex 用**另一种机制**解同一个问题,且 §3.3 那个 v1.2.0 代码块盲区在 Codex 里有现成的完整解。两次独立实现收敛到同一设计判断——这比任何新增论述都强化 ch03 的核心论点(Markdown 反感流式,防御逻辑是必要之恶)。

**ForgeLoopTUI 侧**(ch03 已有,补记只引用不重述):换行符切分 stable/unstable;表格 retreat(发现 split 风险才回溯扫描);v1.2.0 代码块盲区(fence 状态不跨帧)→ v1.2.1 fence retreat 先于 table retreat。

**Codex 侧【亲读】**:

- 状态机三态(`streaming/table_holdback.rs:23-32`):`None` / `PendingHeader{header_start}`(末行像表头但分隔符未到,**乐观** holdback)/ `Confirmed{table_start}`(表头+分隔符对确认,表头起全部保持 mutable 直到 finalize)。
- 扫描器是**增量**的:`TableHoldbackScanner` 只记一行 lookbehind(`PreviousLineState`:source_start + fence_kind + is_header),每个新提交的源行折叠进状态机(`table_holdback.rs:119-159`)。确认条件:前一行 is_header 且当前行 is_delimiter,且两行都不在非 markdown fence 内(`:132-141`)。
- fence 语义:`FenceKind::Other`(如 ```sh)内的表格行跳过;**markdown fence 内的表格仍要 holdback**;blockquote 前缀剥除后仍识别;缩进的 fence 样文本不算开 fence。各有专测。
- **字节↔行数桥接集中一处**:扫描器用字节偏移,队列用渲染行数,唯一换算点 `tail_budget_from_source_start`(`controller.rs:419`);表头前稳定前缀的渲染行数有缓存(`StablePrefixLenCache`,因为密集表格流每个 delta 都触发该路径)。
- **与"最后 block 可变"是叠加关系**:表格确认期,连早于当前 block 的内容都要容忍重排——ForgeLoopTUI 的 stable/unstable 二分没有这一层。成本靠缓存压住。
- **换行门控**(`markdown_stream.rs:87` `commit_complete_source` 只提交到 `rfind('\n')`):未完成的半行表格根本不渲染——防"用户瞥见畸形列后下一帧消失"。
- **代码块盲区的他山答案**:Codex 全程维护 `FenceTracker`;另有一条 code fence 快路径——开着的 fence 直接 append 渲染行、不重解析(`render.rs:140-146`,配 `OpenCodeFence` 状态)。
- **等价性即测试**:增量扫描器与非增量全量扫描函数有逐 chunk 相等性测试;更根本的一条命题——*流式渲染的正确性 = 任意 delta 切分下,「已上屏 + tail」恒等于全量渲染*(见 G 项)。

**补记论点建议**:事前状态机(Codex:增量、常数成本、乐观 holdback)vs 事后回退(ForgeLoopTUI:按需回溯、最坏 O(n)、零常驻状态)——同一问题的两种缴税方式,呼应 ch11 "同一公理的两种缴税"的句式;并明确指出 v1.2.1 的 fence retreat 修复使两家在 fence 语义上对齐。

### B. ch07 新增小节:BalancedEmitter(时间窗)vs 自适应两档(队列压力)

**动机**:ch07 的 BalancedEmitter 回答"chunk 到达频率 ≠ 渲染频率"用的是**时间窗**;Codex 用**队列积压信号**换挡。两个流派并置,补全这个问题的解空间。

**Codex 侧【亲读】**(`streaming/chunking.rs:85-116` 全部参数):

- 两档:Smooth = 每 tick 放行 1 行;CatchUp = 一次清空队列(`DrainPlan::Single` / `Batch(n)`)。
- 进入(满足其一):队列深度 ≥ **8 行**,或最老行龄 ≥ **120ms**;退出(须同时):深度 ≤ **2 行** 且 龄 ≤ **40ms**,且持续 **250ms**(`EXIT_HOLD`);退出后 **250ms** 冷却禁再入;严重积压(**64 行或 300ms**)豁免冷却。
- tick 频率 = `TARGET_FRAME_INTERVAL` ≈ **8.33ms(120fps)**(`tui.rs:84`);动画由 delta 触发 `StartCommitAnimation` 启动、队列空 `StopCommitAnimation` 停表——**空闲零 CPU 空转**,这一点与 ch02 §八 ForgeLoopTUI RenderLoop 的"空闲即停"同构,可互指。
- 策略**只吃两个标量**(队列深度 + 最老行龄,入队时打时间戳),与内容/来源完全解耦;源码自称 source-agnostic。
- 迟滞的设计意图(源码头注释自带症状导向调参指南):不对称(进入用"或"、退出用"且"+持续窗口)防换挡抖动;严重积压豁免防行龄无界增长。
- 对照 ch07 BalancedEmitter 的论点:时间窗是**到达侧均匀化**(突发时延迟线性累积,窗口内中间帧丢弃);队列压力是**消费侧自适应**(低流量下每帧一行保持"打字机节奏",突发下瞬时追平)。前者实现简单、无状态;后者需要队列+时间戳+迟滞,但保证延迟上界。可引申:ch02 §八的 16ms 合帧窗口其实也是一种时间窗,ForgeLoopTUI 整体押在时间窗一侧。

### F. ch23 单章:一行状态文字的状态机

**定位**:小而完整。spinner/shimmer 大家都写过,但"**什么时候显示什么、什么时候必须消失**"的状态机没人写。核心论点候选:*Agent UI 的状态指示难点不在动画,在防闪烁——显示/隐藏的边界条件全是微观决策*。

**Codex 侧素材【亲读】**(`chatwidget/streaming.rs`):

- **reasoning 流不进 transcript**:累积 buffer,提取首个 `**bold**` 作状态行 header(`:232-274`);无 bold 则不显示(静默降级);Thinking/Working 两态还决定终端窗口标题。
- **防闪烁三闸门**:
  1. commit tick 放行内容时**立即隐藏**状态行(`:427`)——流式内容与状态行互斥,否则一帧里既有新内容又有"正在工作";
  2. commentary(前言)完成后不立刻恢复:置 `pending_status_indicator_restore`,只在 turn 仍在运行**且两个流队列全 idle** 时才恢复(`:109-125`)——防止"显示→隐藏→显示"三连闪;
  3. 最终回答完成后,是否恢复取决于**输入队列里有没有 steer 排队**(`:384-391`)——用户已经插了话,马上又要忙,不闪那一下了。
- 动画自驱:spinner 用 `schedule_frame_in` 自请帧(`status_indicator_widget.rs:287`),shimmer 文字渐变(`shimmer.rs:21`)——帧请求与 §B 的全局帧调度合流。
- 顺带一个相关机制可作对照:**中断偏序**——流式写入进行中,ExecBegin/End 等生命周期事件一律进 FIFO 延后(`defer_or_handle`,`:452`),防止状态区与流内容交错乱序。
- ForgeLoopTUI 对照:ch04 的 `operationStart/End` 是"状态行被结果**替换**";Codex 这套是"指示器被内容**压制/恢复**"。两类状态行的所有权不同:前者属于某个工具,后者属于整个 turn。
