## 四、逐项规格

### A. glue03 单章:发送、插话、排队、打断——四个动词的协议契约

- **界面承诺(章锚)**:"我按回车,消息不会丢、不会乱、不会被误解。"
- **核心增量**:
  1. 四个产品动词精确对应四个协议方法,语义分层:发送=`turn/start`(隐式 start-or-steer:空闲开轮,忙则变插话);插话=`turn/steer`(显式,必填 `expectedTurnId`——CAS 乐观并发,不匹配报 `ExpectedTurnMismatch`);排队=`thread/queue/add`(持久进 SQLite,上限 100,idle 自动派发+10s 轮询兜底;注意:隐式路线忙时**不会**自动降级进持久队列——"自动"与"显式"的产品边界);打断=`turn/interrupt`(破坏性原语:任何订阅连接可打断任何 turn,单用户假设)。
  2. 消费时机=轮间隙:steer 接受即入队,绝不打断 in-flight 采样;最早生效点是当前采样+工具链跑完之后(排队式 steering,**无抢占**);唯一被叫醒的是工具层的 sleep/wait。turn 中断时 pending input 直接清空,TUI 侧靠 rejected 队列/interrupt 后重发补偿——灰区全靠客户端策略,core 不管。
  3. 错误契约的弱:core 拒绝 steer 不发事件、错误全走 JSON-RPC response;八种拒绝原因(NotIdle/PendingTriggerTurn/PlanMode/NoActiveTurn/ExpectedTurnMismatch/ActiveTurnNotSteerable/OutputSchemaMismatch/EmptyInput)在协议层全部笼统映射 -32600,结构化 data 只有 ActiveTurnNotSteerable 一种;TUI 靠**英文 message 字符串前缀**解析 actual turn id 重试——对文案的硬耦合,无版本化保障。
  4. 已知缺口照实写:`turn/start` 响应不告诉你"开了新轮还是被插话"(没有 started 标志),被隐式 steer 的客户端只能间接推断——**隐式便利与显式语义的代价差,协议作者选了隐式,把确定性留给显式方法**。
- **素材**:接力执行-1(全文,【接力执行·已交叉确认】,锚点齐全);旗舰文 §3.4(观点句可化用);笔记 #2 §2.4(背景)。
- **互指**:界面 ch21(composer 弹窗状态机——UI 侧,不重讲)、ch22;glue01 §二(错误契约与握手);glue02 §四(时序不变量——steer 场景事件序列是现成例证);glue02 §七(能力声明的真实性)。

### C. glue05 单章:引擎进程是谁的——daemon 的生老病死

- **界面承诺(章锚)**:"升级不打断 agent;版本错位的客户端共存是日常。"
- **核心增量**:
  1. daemon 是什么:常驻共享 app-server 实例 + 每小时自更新 + remote_control 托管;桌面端"壳 0.155、引擎 0.160"共存的机制基础。
  2. 自更新全链:updater 每 60min 跑一轮——**版本检查外包给外部 install.sh(Rust 侧盲区,如实写)**;身份比对(updater 自身 SHA256 vs 新 managed 二进制)决定重启模式;验证重启(flock→SIGTERM 60s 宽限→拉新→10s 内 probe 控制socket 验证);所有权移交:Unix 用 exec 自替换(同 pid 连续),Windows 用 .ready 文件握手。失败路径:无回滚——坏二进制靠下个整点或 CLI 调用兜底;**"没验证起不来就不换 updater"是 Rust 侧仅有的两条硬保证之一**。
  3. 多实例竞争三层防线:daemon.lock(操作锁,串行化生命周期事务)→ pidfile+预留锁+create_new(裁决唯一赢家 spawn;僵死 pidfile 分三态清理;process_start_time 防 pid 复用)→ app-server 进程 startup lock + socket bind 兜底。
  4. 配对仪式一笔带过(细节留给 infra04/手机话题):enroll/refresh/pair,30s 是 enroll/refresh/pair 共用的 HTTP 超时;"4KB 上限"只是错误信息预览截断(**勘误**,见第七节)。
- **素材**:接力执行-3(全文,**注意文首版本差异声明**:本机实机 daemon.pid/SHA256 是新构建观察,0.154 源码口径是 app-server.pid/{pid,start_time}——双轨标注);#14 §5(桌面端同源实证);旗舰文 §4.2(1)。
- **互指**:glue01 §四(三种到达方式)、§五(发布关系定仪式强度——daemon 是"独立发布"的极致形态);glue02 §八(kill -9 之后的对账——daemon 重启与会话存活)。

### D. glue06 单章:审批——server 怎么等一个人

- **界面承诺(章锚)**:"弹窗没人点,turn 不会永远挂着;换个设备还能批准。"(**现状两条都不成立,诚实写**)
- **核心增量**:
  1. 审批是全系统唯一"人的响应是系统输入"的地方——把人放回分布式系统语言:**人是高延迟(小时级)、低可用(会睡觉)、高权威(唯一能批)的节点**。
  2. 现状(0.154)四个事实:core 侧审批是无超时的 oneshot 阻塞等待(唯一兜底是 turn 被中断按 Abort 处理);审批请求不落盘,只活在内存表;UI 断连不清除 pending;重路由唯一机制是新客户端 resume 时重放。单机桌面形态全是合理省略——等的是你自己电脑前的你;"手机遥控 Mac mini"形态下,锁屏瞬间引擎挂死在等人通道上,重启即蒸发。
  3. 补课设计(**本书提出,标"应当"**):审批从 RPC 语义改消息语义——`thread/approval/requested` 通知(幂等 approval_id + expires_at)+ 独立 `thread/approval/respond` 应答(迟到者收 already_resolved 与最终决定)+ 落盘 pending 表;**core 可以一行不改**:胶水层持有 pending 表、执行超时、到点喂 `ReviewDecision::TimedOut`(变体已存在,guardian 在用;语义精确:超时≠拒绝≠中断);双模式投影让老客户端走同步 RPC、新客户端走通知,协商粒度之争被数据模型降维拆掉。
  4. 深层判断:审批治理可外置(guardian/超时/推送全在胶水层),**审批等待不可外置**(oneshot 在 turn 内)——"等待人"是 turn 事务的一部分(turn=事务边界的伏笔,基建 infra04 展开)。
- **素材**:旗舰文 §5.3(成稿,设计建议部分保持"应当"措辞);接力执行-6 §4(等待不可外置的两个源码论证);glue02 §六(迟到的批准——本篇是其"显式等待语义"的机制面展开)。
- **互指**:界面 ch08(权限 UX);glue01 §一(审批是反向 request);glue02 §六。
- **配图建议**:审批超时状态机(pending→escalated→expired→TimedOut;core 视角 escalation/expired 都是"decision 还没喂")。
