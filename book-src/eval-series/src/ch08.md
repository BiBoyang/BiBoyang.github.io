# 这次 bug 在设计稿里：第一次给大项目设计扩展机制

> 第一次给大型开源项目设计扩展机制：五个问题、三份材料、一次立场反转、两面镜子。和系列前几篇不同，这篇没有闭环——设计稿此刻还躺在我的硬盘上等终审，维护者还没看到它。但 review 回路已经先跑了一遍，被抓到 bug 的是设计稿自己。

## 引子：从修 bug 到被邀请谈设计

2026 年 10 月 8 日，我给 [skill-up](https://github.com/alibaba/skill-up) 提的两个 PR 在同一天合并：#265（超时强杀后由框架合成最小 session-result，下游至少有据可查）和 #295（validate 拒绝没有任何可识别 matcher 的 rule_based 断言）。都是这个系列的老熟人——#265 的诞生过程就是[第三篇](/posts/我给-skill-up-报了一个不存在的-bug/)那场误报的反向产物。

同一天我在 skill-up 的 issue [#296](https://github.com/alibaba/skill-up/issues/296) 里提了一个更大的东西：长上下文 decode TPS 衰减评测。论点是瞬时 TPS 随上下文增长而下降（每个 token 都要重读整个 KV cache），实测某部署从 200 tok/s 掉到 100k 时的 80、300k 时的 50；所以 compaction 阈值应该锚定在模型的**半速点**——TPS 降到基线一半的上下文长度，实测 GPT 类部署约 67k，远早于民间流传的 200k。我手里有能跑出这条曲线的 [harness](https://github.com/BiBoyang/dsh-eval-harness)，想给 skill-up 加这条评测轴。

维护者的回复很值得逐句读：框架 scope 保持"任务断言 + 执行时长"的行为评测，**不内置专用测量 loop**；但可以给一条集成路径——custom engine adapter 加自定义指标扩展，测量和 compaction 逻辑归外部；最后一句是："We'd be interested in exploring that general metric extension"，并指了 Harbor 的 ATIF 做参考。

翻译一下：场景被拒了，但**机制被邀请了**。我回了一条 ack：接受边界，承诺研究完 ATIF 带设计稿回来——一个设计细节都没承诺。这篇文章记录接下来发生的事。系列惯例是闭环叙事（事故 → 结论），这篇破例：写到这里的此刻，设计稿还没发出去，结局未定。但等待期间学到的东西已经值回票价。

## 1. 拿到设计题，先把嘴闭上

我给自己立的议程是五个问题：指标数据从哪来（供给）、从序列拟合出标量这种事归谁干（计算）、标量/序列/曲线分别怎么进报告（展示）、schema 长什么样（参考 ATIF）、框架不做什么（边界）。

然后是这条系列反复出现的纪律的又一次应验：**先读一手材料，再开口谈设计**。三份：

- **skill-up 自己的数据流实现**。`SessionResult` 是个封闭 schema，没有任何 extra/telemetry 字段，今天唯一塞自由数据的通道是 artifacts。但数据流是一条直路：`SessionResult` → evaluator 内嵌 → `evalResultToCaseResult` 硬投影进报告 → 各 reporter 渲染。加字段有现成路径，`ObservedModel` 当年就是这么进去的。
- **参照物 Harbor ATIF 的源码**。两个文件加起来 84 行。读完才发现一个文档里不会写的事实：**ATIF 的聚合值是"写出来"的，不是"算出来"的**——schema 里没有任何 reducer，谁产 trajectory 谁负责填汇总数。这个事实直接撑起了我后面最重要的一条设计立场。
- **我自己 harness 的遥测形状**。748 行的 `tps.ts` 里数据天然分三层：样本级（每次请求的 chunk 流、原始 usage）、台阶聚合（每个上下文台阶的中位数）、拟合标量（baseline、半速点、R²）。**数据分层决定通道分层**——chunk 流和原始 JSON 是证据，走 artifacts；拟合标量和台阶序列是展示数据，走 metrics。

## 2. 先例考古：这个代码库里类似问题怎么解决的

设计提案里最容易被维护者打回的是发明新词汇，最吃香的是"遵循你自己代码库的既有模式"。所以我给 skill-up 做了一次"数据选择机制"的普查，找到三层先例：报告投影是编译期钉死的硬投影（用户不可配）；judge context 是 profile 预设 + 逐字段覆盖 + 大小限额（SUP-0004，连"include 超体积自动降级为文件引用"这种细节都有）；跨迭代聚合有 `StatValue`（mean/stddev）和 `unanimous()`（全票一致才显示，分歧置空）两种现成脾气。

但最重要的一条先例不是这一遍找到的，是下一轮被逼着重读才看到的——**先例不是一次找全的。第一遍读代码建的是地图，第二遍带着具体的决策问题去读，才能看到机制。**

## 3. 立场反转：一句"这两个有什么区别"

设计稿初版里，"指标怎么显式影响 pass/fail"这一题我推荐挂在 `rule_based` 的 Rule 枚举里，理由是"不发明第二条判决通道"。自己听着都挺扎实。

讨论时 Owner 回了一句："这两个我还是没明白抉择的原因，这两个有什么区别？"

我回去把代码又读了一遍，发现初版立场建立在不完整信息上。两个候选的真实区别根本不在"放哪好看"：其一，`judge.type` 是单选——挂成 rule_based 规则意味着用 agent_judge 评行为的 case 永远用不了指标阈值，而"行为评分 + 性能阈值"恰恰是 TPS 场景的组合需求，"通用"二字当场不成立；其二，`expect` 层**本来就是**与 judge 类型无关的第二条断言通道——它先于 judge 跑，结果汇入同一条 `Grading.AssertionResults`，失败则短路 judge。我"不发明第二条通道"的理由多虑了，通道早就有，`metric_threshold` 插进去就行，还白赚一个适合性能闸门的 fail-fast 语义。

推荐当场反转。这轮给我最大的教训不是哪个选项对，而是：**当评审方说"看不懂区别"时，正确的反应不是换个说法再解释一遍，是回去再读一遍代码**——看不懂往往意味着选项描述漏了决定性问题。

## 4. 两面镜子：发布前的最后一轮自测

设计稿改到自认能见人之后，发布前我派了两个零上下文的 subagent 做最后一轮，故意给它们正交的任务：**事实核查员**逐条核验稿子里每个 file:line 论断（"SessionResult 是封闭 schema"、"expect 失败会短路 judge"、artifact 上限、连维护者原话都重新从 GitHub API 拉了逐字比对）；**红队**扮演那位维护者，任务是攻击设计本身。都不带我的推理过程，避免被我的结论锚定。

核查员的判决：12 组论断全部属实，外加一处 WRONG——我稿子里写"rule_based 不短路"，是假的，`rule_based.go` 对 failure 规则命中即短路；我想说的区别其实是"它是终端 judge，没有下游可跳"。措辞修正。

红队的判决是 revise-and-resubmit，两个 blocker 都很疼：

- **B1 多轮洞**。stateful 模式下每个 turn 各产出一个 `SessionResult`，而 case 级聚合是**结构体拷贝最后一轮**的结果再覆盖固定字段清单（`buildAggregateResult`，multiturn.go）。我的"per-turn 指标延到 v2"根本挡不住 v1 出事：metrics 字段会搭车成"意外的末轮赢家"，前 n−1 轮静默丢弃，阈值也只绑末轮。"延到 v2"回答不了"v1 发生了怎么办"。
- **B2 脱敏假设**。我稿子里写"metrics 继承 SessionResult 既有的敏感值脱敏"——也是假的。脱敏是逐字段白名单（`maskAPIKey` 一个一个字段地调），新的 metrics map 会不打码直出。照字面实现就是泄密。

两个 blocker 我都亲自回去复核了代码才敢动笔改稿。改法：多轮行为写成显式契约（非末轮丢弃并告警、adapter 在末轮报累计值、阈值绑聚合结果），脱敏改写成显式遍历契约（键、字符串值、描述、单位都打码，限额在脱敏后执行）。

点题一下：这个系列的主线是"裁判本身也要被校准"，每篇的 bug 最后都抓在测量系统自己身上。这一篇的同构之处在于——**这次被抓到的 bug 在设计稿里，而且在维护者看到之前**。核查员抓的是"我断言错的"，红队抓的是"我压根没断言的"。错误好抓，缺席难抓，这就是为什么需要两面镜子而不是一面。

## 5. 沉淀：第一次给大项目做设计的清单

**设计原则**（这次提炼的，下次直接查）：

- 框架聚合统计量，adapter 派生语义量。框架懂 mean/stddev，它不懂半速点是什么。
- 指标是数据，不是判决。报什么展示什么，断言只点名。
- 数据分层决定通道分层：展示就绪的值进 schema 字段，证据性原始数据进 artifacts。
- 审查力度来自机制，不来自纪律——自动校验、自动断言、固定表位、可 diff，不靠审查者更认真。
- 代理决策只替对方做可逆的决定：schema 不可逆，留给人拍板；渲染可逆，可以代定。

**过程方法论**（按杀伤力排序）：

1. 先读后写，三份一手材料读完再开口；参照物读源码不读文档。
2. 锚定维护者原话的精确射程，引用原文逐条对应；ack 接受方向但不承诺任何细节。
3. 先例优先于发明；找不到先例才发明，并说明为什么。
4. 给决策点不给开放式问题——维护者只需要确认或推翻，不需要从零想。
5. 立场可以被新证据推翻，推翻过程本身就是文章素材。修订记录比永远正确更有说服力。
6. 发布前用两面镜子自查：核查验证已断言的，红队发现缺席的。
7. 边界写两遍：Non-goals 一遍，结尾重申一遍，防 RFC 阶段被加需求。
