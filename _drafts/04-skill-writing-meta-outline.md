# 文章大纲：skill 写作的元规则（WRITING.md）

> 系列第四篇（合集篇）。统一叙事：踩过的坑 → 规则 → 规则背后的权衡 → 读者能单独拿走的东西。

## 标题方向

《给 AI 写规则的规则》

## 一、开场：skill 写到第九个，问题变了

- 前九个 skill 的问题是"写什么"：把踩过的坑固化成纪律
- 第九个之后问题变成"怎么写"：质量开始靠临场发挥，每条新规则都可能稀释旧规则
- 于是有了 WRITING.md——写 skill 的 skill 规则

## 二、六条元规则（每条：一句话规则 + 防什么 + 一个例子）

1. **废话测试**：每行只有改变模型默认行为才配存在。"要仔细""要全面"是花上下文买沉默——判断不了就假设是废话，删
2. **给目标，不给脚本**：写清"什么算完成、拿什么证明"，路径留给模型。步骤写到不可替代的判断点为止，再细是花钱买僵化
3. **清单只收敛，不堆积**：新条款先问是不是既有原则的实例——是就折叠进去。近义条款平铺三条，读的时候一条都记不住
4. **规则不带来历**：规则文本只说防什么、怎么做；来历放 commit message 或末尾踩坑表。对照：文章恰恰是把来历讲出来的地方——规则要可执行，文章要可理解，分工不同
5. **description 写给路由器，不写给人**：触发率是 skill 的生命线；穷举口语触发词（"看看代码""又挂了"），补"不管 X"划清边界。写法再好，不触发等于零
6. **载荷放对层**：跨场景约束进全局 AGENTS.md、场景触发进 skill、纯知识进笔记——不为知识做 skill

## 三、怎么借鉴不抄袭

- 从 Waza 学到的：上面的骨架；从 Waza 没学的：分发基建、CI 套件、重输出模板——个人集合不需要
- 借鉴的正确姿势：学判断标准，不学文本；每条规则用自己的语言和自己的坑重写一遍
- 诚实交代：这篇文章本身遵循"规则不带来历"的反面——文章就是讲来历的地方

## 四、验收：dogfood

- skill 改动提交前，用自己的 code-review 纪律审自己的 diff
- 写规则的人首先受规则约束，这套东西才可信

## 五、尾声：火候

- 合集名叫"火候"：知道什么时候该等、什么时候该收、什么时候该关火
- skill 不是 prompt 技巧合集，是把自己的工程判断外化成可复用的纪律
- 元规则的意义：让第五条纪律和第一条一样锋利

## 六、带得走的清单

- 废话测试、目标导向、清单收敛、路由器视角、分层放置——写任何 prompt/规则文档都能用
