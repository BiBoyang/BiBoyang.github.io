# 文章大纲：recover-from-errors

> 系列第二篇。统一叙事：踩过的坑 → 规则 → 规则背后的权衡 → 读者能单独拿走的东西。

## 标题方向

《报错之后，最大的风险不是错误本身》

## 一、开场：越修越偏的那个晚上

- 现象：AI 修报错，猜参数、换路径、换工具，每一次"试试看"都往上下文里塞噪音；几轮之后已经在修一个根本不是问题的问题
- 对照案例：一次 GitHub 网络抖动——正确动作是原命令有界重试，而字面上的"禁止盲目重试"规则反而会让人僵住（规则本身也需要分类）

## 二、定性：漂移比错误可怕

- 错误是明处的：报错信息摆在那
- 漂移是暗处的：动作离目标越来越远，但每一步看起来都"在解决问题"
- 所以恢复流程的第一目标不是消除报错，是防止偏航

## 三、设计 1：先分类，再动手

- 瞬时/环境类（超时、TLS 失败、rate limit）：允许原命令原参数有界重试，重试前用只读探针验证通道——"这次为什么应该不一样"的答案就是探针证据
- 确定类（参数错、路径错、断言失败）：同参数重试零价值，直接进恢复流程
- 分不清：先留证，用只读操作缩小层面——不带模糊判断直接改

## 四、设计 2：留证先行

- 重试或修复之前，先存完整报错原文、退出码、日志路径
- 为什么：上下文滚动之后诊断依据就没了；硬停止时的"卡点描述"全靠它

## 五、设计 3：回锚点

- 核心一问："我刚才这个动作，是方案里明确要求的吗？"
- 方案内执行错 → 修这个具体问题；方案里没这一步 → 立即停止这条线，从最近的正确节点重走
- 修因不修表："文件不存在"要问为什么不存在，而不是换个文件继续
- 修完回原点位验证：用原始失败的那条命令（不是变体）确认——防止修复本身引入新偏差

## 六、设计 4：跑完 ≠ 成功

- 真实案例：后台任务状态 completed，日志里却是 fatal，push 根本没上去
- 规则：命令结束必须核对退出码、关键输出、目标状态，再推进

## 七、设计 5：硬停止——知道什么时候认输

- 三个停条件：同一点位修 3 次不过、要继续就得动方案外的东西、原因超出当前知识范围
- 停的时候交出三样东西：当前状态、已改动的内容、卡点描述
- 不硬试、不擅自回滚、不假装修好——认输也是交付物

## 八、三条红线

- 禁盲目重试（每次重试先说"这次为什么应该不一样"）
- 禁为消除报错扩大改动范围
- 禁静默绕过（`|| true`、吞异常、注释掉报错代码）

## 九、带得走的清单

- 先分类、留证、回锚点、核结果、敢停手——不装 skill 也能用
