# 文章大纲：wrap-up

> 系列第三篇。统一叙事：踩过的坑 → 规则 → 规则背后的权衡 → 读者能单独拿走的东西。

## 标题方向

《提交之前，谁来喊停——交付链路的确认语义》

## 一、开场：AI 提交代码的两种极端

- 极端 A：什么都不问，commit push 一气呵成——爽，直到它把不该推的推上去
- 极端 B：每一步都问——"要 add 吗""要 commit 吗""要 push 吗"，三轮下来人比 AI 累
- 核心问题：确认的摩擦是一笔预算，应该全部花在真正的不可逆点上

## 二、四种模式为什么要分清

- `提交` = commit + push；`推送` = 只 push；`收尾` = 日志+README+校验+草案；`收尾并发布` = 追加版本和 tag
- 边界混了的后果：想收尾被直接推了，想提交被塞了一堆 session 日志
- 演化故事：提交语义从"只 commit"改成"默认 commit+push"——因为用户说"提交"时的意图九成九是"推上去"，区分语义不如对齐意图

## 三、确认语义的演化史（本篇主线）

- 三次修订，每次都来自一次真实摩擦：
  1. 用户直接说"提交吧" = 已授权，不再二次等 `o`
  2. 改动已展示并获确认后，不再单独给 commit message 草案——草案只留给「收尾」（因为收尾时改动未经过目，草案是那道闸门）
  3. 发布链路只在草案处确认一次，打 tag 不二次确认
- 一句话原则：同一件事不确认两次，但没有任何事不确认就出去

## 四、闸门设计：每个闸门防一件真事

- 显式 add：防 `git add .` 把无关改动捎进去
- 敏感文件两层闸门：先查文件名（.env/key/pem），再扫内容里的凭据字样——文件名会漏，内容也会假阳性，所以两层
- 范围闸门：staged 里出现任务范围外的文件就停
- 主分支闸门：在 main 上且没明说直推就停——防"顺手推主分支"

## 五、push 被拒绝时的纪律

- 禁止自动 `git pull --rebase`：rebase 是改写历史，必须经过人
- 只读排查三件套（status / fetch / log --left-right），把分叉原因摆出来，由人决定
- 为什么这条值得单列：自动化到一半的破坏性操作最难收拾

## 六、带得走的清单

- 模式分清、确认预算花在不可逆点、闸门显式化、被拒先只读——不装 skill 也能用
