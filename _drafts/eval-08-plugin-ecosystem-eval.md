> **系列 · 我的评测工具链**（持续更新）· 第 8 篇
>
> 全部篇目、阅读路径与系列沉淀的纪律见 [系列导读](/eval-series/)；上一篇：[考官带伤阅卷](/posts/考官带伤阅卷-对-Agent-Skill-做故障注入的完整性实验/)

> 给三个高星 dsh 插件建门禁：一个 7000★ 的装完即死，一个差点被我冤枉，一个全绿得理所当然。主角不是插件，是三个方法论问题——oracle 从哪来、锅怎么分、分母是谁。全程写实，包括我判错又推翻的那次归因。

# 1. 开场：前七篇测自己，这篇测别人

这个系列一路测过来，靶子都是**自己的东西**：自己的插件、自己的 skill、自己用的 CLI。[第 5 篇](/posts/回答被截断-你的-CLI-知道吗-四个工具-六种故障-108-格矩阵-和一个差点发布的错误结论/)测「流」（截断检出矩阵），[第 7 篇](/posts/考官带伤阅卷-对-Agent-Skill-做故障注入的完整性实验/)测「文件」（带伤的 SKILL.md）——同一套检出思想的两次迁移。

这一篇是第三次迁移：**测别人的生态**。

靶子是 dsh（[deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)）插件榜上三个高星项目：dsh-routing-suite（约 7000★，路由/注入器）、modlens（约 4000★，视觉工具）、dsh-agent-teams（约 1800★，多 agent 编排）。星数是 2026-09-26 从 GitHub API 现拉的——这个系列的老规矩，版本和日期先进报告。

测别人的东西和测自己的，差别只有一句话：**测自己的工具有 spec，测别人的生态没有。** 你不知道作者的设计意图，只有一份 README、一个安装命令、和一堆你愿意相信的星。oracle（判定依据）的缺席是后面所有故事的源头，它逼出三个新问题：**oracle 从哪来？锅（失败的归因）怎么分？分母（结论对什么成立）是谁？** 这篇就是这三个问题的实战记录。插件的测评结果只是证据，主角是方法。

# 2. 分母是谁：你只能测装得上的

先说一个容易被跳过的前提：生态评测的分母从来不是「全部插件」。

dsh 插件最大的目录 awesome-dsh-plugin 收录约一千五百条，收录规则是提个 YAML 就进——**没有安装验证**。另一份清单（AdamPlatin123/awesome-dsh-plugins）的作者较真，在容器里逐个真装：9247 个候选，1673 个实测，结果是 **979 可用 / 600 不兼容 / 94 待定**。装得上的只有六成。也就是说，任何生态测评能给出的结论，天然只对「可安装的头部」成立——把安装成功率本身做成一层数据，比假装它不存在诚实得多。

选品过了三道筛。**headless 可测**：我的 harness 驱动的是 `dsh --profile headless`，热度榜头部一半的 UI 类项目（桌面壳、侧边栏、皮肤、TUI）在这个管线下结构性不可测，剔掉。**安全定位**：榜上混着破甲/红队类插件，剔掉——测评它们的报告写出来定位很尴尬。**类型覆盖**：剩下的里面挑三个不同类型的——管线型（routing-suite）、工具型（modlens）、编排型（agent-teams）。后来证明这个挑法运气好：三种类型恰好对应三种 oracle 形态，第 4 节展开。

四层漏斗就这么立起来：**人气 → 可装 → 行为正确 → 故障韧性**。本来我以为后两层才会有戏，结果每一层都出了真东西。

# 3. L1 可装层：安装不是前置条件，是第一层数据

第一个插件就给了我一课：routing-suite 的「一键安装」，命令是成功的，插件是死的。

```console
$ dsh plugin --profile headless add <codeload tarball #1952733>
✓ 安装成功（exit 0）
$ ls .../dsh-super-injector/injector/
package.json  src/        # ← lib/ 缺席：prepare 构建被 pnpm 11 拦截
```

根因：这个插件靠 `prepare` 钩子在安装时自动构建——它的 README 写得明明白白，「`github:` 装配由 prepare 钩子自动构建」。而 **pnpm 11 改了默认行为：依赖的构建脚本一律拦截**，除非在 `allowBuilds` 里显式批准。设计没有错，是 pnpm 把路从作者脚下抽走了——[第 4 篇](/posts/CI-红-本地绿-一次-平台差异-误诊-和-merge-干净不等于语义兼容/)讲「merge 干净不等于语义兼容」，这是它的安装版：**设计文档没有变，环境的语义变了。**

顺手还抓到另一个生态级陷阱：**npm 同名错位**。npm 上的 `dsh-routing-suite@0.1.2`，repository 指向的是 `dragonbaba` 的另一个账号，不是这个 7000★ 的仓库——谁要是 `dsh plugin add dsh-routing-suite`，装到的是个不相干的包。裸名的 `modsearch` 同样中招。反过来，agent-teams 用裸名搜是 404，真身是 scoped 的 `@nanmicoder/dsh-agent-teams`——**裸名 E404 不等于没发 npm。** 三条放一起，安装指引的正确形态只剩一种：全限定、钉版本、写明出处。

所以 L1 的结论改写了：安装不是测评开始前的静默过滤器，它就是第一层数据。「装得上吗、装的是不是那个东西、装完是不是活的」——三个问题每一个都有真实失败率。

这一层也有工程后续：harness 给隔离环境补了 allowBuilds 解锁（registry 形态按包名预置；tarball 形态 pnpm 不许按名授权，改成识别构建拦截→收割 pnpm 自己打印的 key→重试的混合方案，授权边界与手工解锁完全同构）。解锁后 routing-suite 装上、激活、跑通了全部用例。证据和建议（照作者自己给 graded 组件发预构建 `.tgz` 的惯例，给 injector 也发预构建）整理成了 [issue #152](https://github.com/yjh051108/dsh-routing-suite/issues/152)——提 issue 不提 PR，理由在第 7 节一起说。

# 4. L2 行为层：oracle 从哪来

没有 spec，oracle 只有三个来源，抓的虫不同，措辞的谨慎也不同。

**README 承诺**——测的是「名不副实」。把作者宣称的功能落成可判定断言：modlens 说「图片给它，它还你结构化 JSON 证据」，那就断言 `modlens_read_image` 必须真实被调用、输出必须带工具标记（不许用 bash 兜底答对，这是[第 1 篇](/posts/从-trace-到-eval-trace-设计-Agent-评测方法论-一个评测-harness-的实现-和它抓到的上游并发-bug/)就立过的覆盖断言）。**行为钉版**——测的是回归，把首次运行的行为固化为基线，将来变了就红；这里措辞要小心，行为变了不等于行为错了，红只意味着「该有人来看一眼」。**宿主不变量**——测的是相容性，「插件在场时，宿主原有的故障处理不能被破坏」，这是最有杀伤力的断言，因为它不依赖插件的任何文档。

三个插件恰好各占一种形态：routing-suite 是行为规则（路由预设是否按声明生效），modlens 是工具输出结构，agent-teams 是 trace 事件序列（`agent_teams_status` 的调用与转述）。三种 oracle 都能从 README 反推出来，这是好消息。

坏消息是第四种情况的存在：**有些承诺落成不了可判定断言**。modlens 的「视觉成效」就是——本机没有配置成功的 vision 引擎（DeepSeek 是纯文本模型，插件的 claude-cli 复用路实测败于 `unrecognized_model`），「它看图看得好不好」在这个环境里无法判定。这时候正确动作是**在报告里如实标「不可判定」**，而不是写一条永远通过的橡皮图章断言假装覆盖到了。[第 3 篇](/posts/我给-skill-up-报了一个不存在的-bug/)的教训在这儿复用：证据质量不保证结论正确，它保证的是纠错的速度——「不可判定」三个字就是给将来的纠错留的抓手。

反面教材之外还有正面案例：agent-teams 全绿不是偶然——它仓库里自带 `verify:harness-contract` 的 TDD 链，一千八星还自己给自己建门禁的插件，整个榜上都不多见。

# 4.5 原则分层：第一篇说过「不用替身」，这篇为什么又用了

写到这儿必须处理一个矛盾，不然老读者要挑刺。

第 1 篇我立过一个立场：「读真实 trace，**不用 LLM 替身**……替身测通过的系统上线照样崩。」而这次 L3 层的 chaos 用例恰恰全跑在 mock 上——自己打自己脸？

不矛盾，是分层。第 1 篇的原则管的是**行为语义**：prompt 怎么组装、模型怎么决策、工具协议怎么走——这些换上替身，测的就不再是那个系统。而 mock 管的是**协议故障注入**：要流按要求截断、丢终止事件、发半个事件——真实模型不会配合你确定性犯病，这个维度里模型的智力与结论无关，逐字节可控的 mock 反而是唯一可信的考题。四层漏斗就是这个分层的具身：L2 冒烟走真实 API（行为），L3 chaos 走 mock（协议）；mock 的保真风险由[第 6 篇](/posts/给流式协议造故障-三协议-mock-once-注入-字节级送达证明-和-strings-阴性不等于代码不存在/)的黄金样本校准兜底。第 1 篇的那段话这次也补了一条补记，把这个分层写明了。

成本数字顺带对照：第 1 篇 12 条用例烧约 12 万 token；本轮真实 API 部分（两条冒烟）合计 **20116**，chaos 层为零。该省的地方省，该花的地方花。

# 5. L3 韧性层：chaos 是归因工具，不只是压力测试

L3 的做法：裸 chaos 基线（第 6 篇固化的六种协议故障行为）先跑一遍，再把插件挂进 mock 环境跑同样四格（F0 对照 + F1/F4/F5）。判定口径一句话：**挂载后宿主行为变了，账才算到插件头上。**

结果：两个可测插件（modlens、agent-teams）4/4 全绿；routing-suite 解锁后重跑也是 4/4——F0/F1 自愈、F4/F5 检出 exit 1，**与裸基线逐格一致**。

全绿也是结论：一个直接坐在 LLM 请求链路上的 7000★ 注入器插件，不破坏宿主的故障检出和恢复。这种「没出事」的确定性，只有对照组能给你——没有裸基线，「全绿」和「没测到」长得一模一样。

# 6. L4 归因层：一次推翻自己的归因

本篇的戏肉，是我自己的一次误判。

modlens 的 L2 第一次跑，现象非常「清楚」：在真实 home 新建的 profile 里装上插件，首次启动直接挂死，三十分钟没有输出。安装日志干净、profile 结构正常、插件是 npm 正规军——**「插件启动阻塞」**，归因报告第一版就这么写的，证据看着很硬。

按归因纪律，下结论前补一个裸对照：全新 profile，什么都不装，首启。

也挂。

真凶根本不是 modlens，是宿主 dsh 自己的一个 bug：**真实 home 下新建 profile 的首启必挂**（老 profile 正常、隔离 home 首启也正常；`lsof` 零连接、`pgrep` 无子进程、stdin 重定向无效、`sample` 抓出来是纯事件循环空等）。我归因报告里的「证据很硬」，每一条都同时兼容两个完全相反的解释——插件阻塞，或者宿主挂起。区别它们的不是证据强度，是一个变量控制正确的对照组。

这个系列一路都在记这种账。第 3 篇：观测会骗人（mtime 是真的，数字是一致的，结论是错的）。第 5 篇：考题也会骗人（mock 方言说错，制造假阴性）。这一篇补上第三句：**对照组选错也会骗人**——我当时用的对照是老 profile，混淆变量是「新 profile 首启」而不是插件。正确的对照不是随手抓一个「正常环境」，是同变量控制。

还有一条执行纪律顺手固化下来：modlens 的归因文件里，**v1 的错误结论和推翻过程原样保留**，没有改成「一开始就判对了」。归因文件的价值恰恰在于记录错误——下次再遇到「证据很硬」的时刻，它提醒你硬证据是怎么兼容两个故事的。

# 7. 三只 bug（系列传统：测到什么就报什么）

这轮测评一共抓到三只真 bug，按归属分三家。

**宿主 dsh：新 profile 首启挂起。** 就是上一节那位真凶。报障时发现一个生态冷知识：deepseek-harness 仓库的 Issues 是关的，报障走 Discussions——所以这份是 [Discussion #7978](https://github.com/deepseek-ai/deepseek-harness/discussions/7978)，复现步骤（三个独立新 profile + 空 profile 全复现）和排除证据（lsof/pgrep/stdin/sample 四路）都附了。

**harness 自己：超时杀不掉进程树，runner 永挂 34 分钟。** 裁判也交了卷。runOne 超时只 SIGKILL 直接子进程，包装器形态（`pnpm -C … dsh`）的孙进程被孤儿化，占着 stdio 管道不放，`close` 事件永远等不到——整条 runner 挂死，实测挂了 34 分钟才被我发现。修复是进程组杀（`detached` + 组属探测后负 pid 组杀），回归测试专门断言「孙进程必死」。这个系列说「裁判也需要校准」，这次是字面意思：评测工具自己的超时机制，被它要测的场景打穿了。

**routing-suite 安装路径：提 issue 不提 PR。** 就是第 3 节的 [issue #152](https://github.com/yjh051108/dsh-routing-suite/issues/152)。为什么只提 issue：修法（给 injector 发预构建产物）我建议了但没有亲手验证过——**提 PR 得拿出能跑的方案，提 issue 只要附上能复现的证据**。前者是空头承诺，后者才是诚实可行动。这和第 3 篇「issue 里的修复建议是假设不是承诺」是同一条纪律的另一面。

# 8. 沉淀：生态评测的四条纪律

给也要去测别人生态的读者，四条能直接拿走的：

1. **分母写出来**。采样框、安装成功率、剔除名单全进报告。结论只对「可安装的头部」成立——把这个限定写进结论本身，而不是藏在脚注里。
2. **oracle 分三层**。README 承诺（测名不副实）/ 行为钉版（测回归）/ 宿主不变量（测相容性）。写不出可判定断言的，标「不可判定」——橡皮图章断言比没有断言更坏。
3. **归因先跑裸对照**。红格没有对照组不许下结论；对照组选错比没有对照组更危险，它给你的错误结论配证据。
4. **成本透明**。版本、测试日期、token 开销进每份报告。本轮真实 API 合计 20116 token，两只裸对照探针另计——读者有权知道结论的价格。

# 9. 附：子 agent 截断的三家设计对照（源码侧，零 token）

本轮本来有个候选后续：编排级 chaos 压力测试——多 agent 场景下，子 agent 的回答被截断后喂给队长综合，是最坏形态的静默截断。动手前先花十分钟查了源码，然后把这个项砍了：**dsh 在设计层就没有这个洞**——子 agent 截断是显式失败（`stopReasonError` 生成「subagent run hit its token limit before finishing」），半截正文只作诊断保留、不作产出，未知终止原因一律映射 error，注释写明「never silently 'completed'」。

顺手把三家的设计摆在一起，比实测便宜得多：

| | 子 agent 截断 | 主 agent 截断 |
|---|---|---|
| kimi-code | 硬检查显式失败 | **静默当成功收下**（[issue #4012](https://github.com/MoonshotAI/kimi-code/issues/4012)） |
| dsh | 显式失败 + 一句人话 | 检出但裸 exit 1 无文案 |
| codex | 重试→显式错误（亮牌） | 同一条链（第 5 篇 L3 实测） |

先查源码再决定烧不烧 token——这本身也是方法：最贵的那轮实验，往往可以被十分钟的阅读替代。
