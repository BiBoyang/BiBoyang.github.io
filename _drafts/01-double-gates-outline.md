# 文章大纲：双闸门（plan-first × code-review）

> 系列第一篇。长度不限，以讲明白为准。
> 统一叙事：踩过的坑 → 规则 → 规则背后的权衡 → 读者能单独拿走的东西。

## 标题方向

《AI 编码的质量不取决于编码——我给它装了前后两道闸门》

## 一、开场：两条推文之争

- 推文 A：AI review 容易掉局部陷阱（默认方案正确、只在方案内打补丁）、挤牙膏（每轮挑新问题刷存在感）
- 卡颂：review 挑出来的偏差，根因多半是需求没对齐，AI 只能脑补
- 我的判断：两人都对了一半。偏差的根因分布在**三处**——需求、路线、实现；单靠任何一道工序都接不住
- 亮答案：事前一道闸门（plan-first），事后一道闸门（code-review），中间用一份 spec 连成闭环

## 二、第一道闸门：plan-first（动手前）

- 闸门本体：方案未经确认，一行代码不写；`开干`/`o` 的低成本确认——摩擦要刚好
- 第 0 步需求拷问：把"以为都默认、其实没写明"的地带逼出来（边界、异常流、幂等、降级）；答案固化成「需求规格」当唯一事实来源；一次最多 3 问——拷问不是审讯，节奏不能断；需求明确就跳过
- 两条围墙：确认前只读（防"查着查着顺手改了"）、禁可复制 diff（那是绕过闸门的隧道）
- 两种入口分流：bug 先根因（根因未确认只出诊断方案，拒绝"先跑起来再说"）/ 新功能压设计
- 候选方案数量规则：中高风险必须两个截然不同的方案；低风险只给一个，禁止硬编陪跑——数量纪律防的是"为显严谨而凑数"
- 方案五要素里重点讲"待拍板决策点"：把用户注意力集中到真正需要他的地方，十秒内知道该拍什么板
- 存疑先探针：spike/示踪弹最小端到端打通，探不通回炉换方案，探针成本写进取舍

## 三、第二道闸门：code-review（动手后）

- 立场：判断指南不是勾选清单——为什么我不给 AI 检查表
- 先审路线再审代码：局部陷阱的解药；但触发式，不重复挑战已定路线——**"已定路线"往往就是第一道闸门拍的板，两道闸门在这里衔接**
- 证据门：高严重度必须给齐位置/触发条件/现有防护为何失效，给不齐就降级；无证据不把理论可能写成 bug
- 一轮查透不挤牙膏：复审冒出"早就存在的新问题"算第一轮失职；没有新发现直说；收益递减喊停
- 跑完 ≠ 成功、假绿不算绿

## 四、闭环：spec 是两道闸门之间的传送带

- 正向：plan-first 的需求规格 → code-review 拿它对照"实现是否匹配声称的意图"
- 反向：review 发现偏差根因在需求没写明（脑补偏差）→ 不在代码层打补丁，回 plan-first 第 0 步补 spec
- 一张图收口：需求 → 方案 → 实现 → 评审 →（回需求 / 回方案 / 放行）

## 五、权衡与代价（诚实段）

- 双闸门不是免费的，简单改动全走一遍是浪费
- 每个严格点旁边都留了低成本出口："直接改"可跳闸门（高危例外除外）、需求明确可跳拷问、路线已定可跳路线评审
- 设计原则一句话：默认从严，出口从简

## 六、带得走的清单

- 不装我的 skill 也能拿走：开工闸门、需求拷问、路线先行、证据门、spec 闭环
