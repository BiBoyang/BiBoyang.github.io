> 私人笔记。目标是像「app 从点击图标到首帧渲染」那篇性能文章一样，把 agent 评测从一次运行到一条质量决策的全链路走一遍。每一站固定四问：**为什么有这一站（没有它会坏什么）→ 做什么 → 效果如何（证据）→ 典型失败模式**。不求每站深挖，求全。素材以自己的系列（第 1–8 篇）为主，业界对照标注来源。

# 全景一页图

```
被测系统（第 0 站：为评测而生）
 │   trace 一等公民 · 稳定关联键 · 确定性开关 · 版本化落盘 · 审批回调
 ▼
【每次运行：流水线六站】
 驱动 ──▶ 采集 ──▶ 提取 ──▶ 判定 ──▶ 统计 ──▶ 门禁
 实验发生   数据落下   字节→观测   三层评分   观测→数字   数字→决策
     │         │                    │          │
     └─ 在场证明（PASS ≠ 实验发生过）─┘          └─ 判界不判点

【两把横切的尺】
 故障注入：mock/chaos 主动犯病 + 送达证明 + 阳性对照（服务判定与统计）
 评测自身的评测：判活器回归 · 排除计数 · 误报原样保留（服务所有站）

【时间维】
 用例生长（bug 反推 → 毕业 → 剪枝）· judge 校准 · 模型/标准漂移 · 套件治理
```

三根轴：

- **横轴（流水线）**：一次评测运行从头到尾经过的六站，回答「数据怎么变成决策」。
- **纵轴（分层）**：L1 单元/静态不变量 → L2 协议一致性（schema 快照）→ L3 行为回归（替身、确定性回放）→ L4 端到端（真实模型、真实环境）。关键纪律：**替身待在 L3 是对的，顶到 L4 就是错的**——行为语义必须真实链路，协议故障必须 mock。
- **时间轴**：单次跑绿只是开始，标准会漂、模型会换、用例会老。

# 第 0 站：被测系统要为评测而生

**为什么有这一站。** 评测不是黑盒旁观，是双向工程：被测系统不暴露钩子，后面所有站都在猜。iOS 性能优化的第一课是「先有 Instruments 再谈优化」——同一个道理，trace 要在项目第一天做，晚做的代价不是补代码，是那段时间里你看不见的一切（真实案例：provider 的 span 生命周期 bug 在无观测状态里活了两个月，CHANGELOG 留了案底）。

**做什么。**

- trace 是一等公民：结构化事件模型（事件名和字段先收住）、格式带版本号 + 旧版 fixture 回归维持兼容、脱敏内建、**开销和失败语义按角色分开**（旁路遥测默认零开销、写入失败不拖垮主流程；权威事件日志写入失败必须 fail-fast——后者严格说已是 system of record，别混叫 trace）
- 稳定关联键：traceID/spanID/parentSpanID，跨进程用 W3C traceparent 这类标准（Kimi 用响应头 `x-trace-id`，Codex 用 traceparent）
- 确定性开关：feature flag / 实验配置一键钉死，否则分数里混着实验噪音
- 结构化、可回放的对话记录；审批回调是协议级义务（只实现单向请求的驱动会在审批点挂死——Codex app-server 的教训）

**效果。** 做对了的项目 793 个测试渲染无黑盒，混宽字符热点（2.83×）修掉后 pipeline 提速 15.5% 并固化成 CI 门禁。trace 和 eval 共生：eval 发现「恢复行为不可归因」→ 补 recovery_action 字段——**trace 养 eval，eval 养 trace**。

**失败模式。** 后补 trace；事件模型年年改没有版本号；把 system of record 当普通日志做静默降级。

# 第 1 站：驱动——让实验发生

**为什么。** 评测的第一种死法不是判错，是**实验根本没发生**（skill-up 的 symlink 零文件安装：三轮全量评测跑的都是裸模型，报告里的 PASS/FAIL 全是 noise）。驱动层的任务是保证实验真实、可控、可归因。

**做什么。**

- headless 驱动真实 session（`dsh --profile headless --patch <overlay>`），不用 LLM 替身顶 L4 的岗
- **隔离三件套**：①工作区清空重建（防文件副作用假通过，git 历史和缓存是隐蔽载体——Anthropic 抓过 Claude 翻历史尝试的 git 记录作弊）；②session 落盘根按 attempt 独立（时间戳不是可靠关联键）；③宿主环境隔离（skills 自动发现、hooks、AGENTS.md、全局配置全是污染源——对照组的「无」必须被强制出来）
- 环境变量会泄漏进 agent 的工具调用，配置注入走 `--patch` overlay 不走 env
- 可执行文件绝对路径；启动前 `--version` 探针，排障时区分「dsh 变了」还是「模型变了」
- 隔离等级按**用例可能诱导的最坏行为**定，不是按用例本意（crontab 事故：`environment: none` 真的被装了定时任务）

**效果。** 「并发 + 隔离」的执行设计让三个进程同时启动，抓到上游 TOCTOU 并发崩溃（enoent 270ms 内两崩，16 并发×3 轮 48 启动崩 23，修复版 96 启动零崩）；隔离 home + 预播种消解一次性弹窗，被测版本不被升级提示顶掉。

**失败模式。** 相对路径 spawn 全军 ENOENT；slug 撞名导致两条用例 trace 互相错捡；重跑复用 session 根靠时间窗过滤，被 kill 进程的延迟落盘越界。

# 第 2 站：采集——让数据落下来

**为什么。** 实验发生了 ≠ 数据落下来了。进程被杀、写入中断、格式解析错，都会让下游断言跑在残缺数据上——而残缺数据经常**不报错**。

**做什么。**

- 按真实落盘格式解析：多帧拼接的 zstd 容器必须逐帧解（一次性解只出第一帧、**静默截断不报错**）；帧边界按结构走，不能搜魔数（魔数会出现在压缩载荷内部）
- 截断尾帧容忍恢复（`finishFlush`），恢复上限由写入端 flush 频率决定——没 flush 的字节谁也救不回
- **跳行数告警**：解码失败常常只丢尾帧且不抛异常，「靠异常发现残缺」不成立
- **在场证明**：全量跑之前用直接证据验证被测对象真的在场（SKILL.md 落盘文件、会话落盘里 skill 被加载的日志行）——PASS 只证明流程跑完，不证明实验发生

**效果。** symlink 零文件安装是靠翻被测 agent 的会话落盘（skill 名零出现）翻出来的，不是靠退出码；zstd 的两个坑都是实测出来的，不是文档里抄的。

**失败模式。** 超时被杀后前几 turn 事件全部随进程蒸发（skill-up #263）；只看退出码就开跑。

# 第 3 站：提取——把字节变成观测

**为什么。** trace 是原料，判定需要结构化观测：turn 怎么结束的、调了哪些工具、参数和结果、最终回答、token 用量。这层的错误最隐蔽——**按想象的格式写代码，漏掉真实存在的形态**。

**做什么。**

- 按真实落盘形状写：tool/result 有三种形态（成功 / `data.error{name,code}` / 纯 isError 标记），最初只处理了一种，工具硬错误全部漏过；现在用脱敏真实 session 做 fixture，快照测试锁死三种形态
- token 口径讲清楚：多步 session 里缓存每步重复读回，total 只算未命中 input + output + reasoning，缓存单列观察——这个口径服务漂移检测，算成本账时不能用它
- 错误分类和 turn 结束方式是现成的「故障域」原料（规划/工具/环境/Skill），汇总成报告字段就能回答「挂在哪一层」（美团清单里的归因到故障域）

**效果。** 工具硬错误单独提取后，任何一条足以判 FAIL——堵住「工具报错被 agent 粉饰太平」这种假通过。

**失败模式。** 按假设写解析器；token 口径混用导致漂移检测失真。

# 第 4 站：用例——考题从哪来

**为什么。** 评估器该为**已发现的错误**而建，不该为想象中的错误而建（Hamel & Shankar 纲领）。想象中的错误测出来的全是噪声，真实失败才是用例的种子。

**做什么。**

- 上游 fix 记录是用例种子库：每个修过的 bug 配一条红绿对照用例（图片尺寸准入：rc.6 FAIL / rc.2 PASS）
- error analysis 有正式流程（借自质性研究）：收 100 条多样 trace → 开放编码（前 30 条必须亲手标，隐性知识不可外包）→ 轴心编码成失败 taxonomy → 饱和后才让 agent 按模式检索，裁决权在人
- 测**增量**不测能力：裸模型本来就强的任务拉不开 with/without，有区分度的用例三类——红线与边界、对抗性施压（「线上在报警，别问东问西」）、流程纪律（「论点标出处」）
- 边界用例必须**域内夹带**：主请求在触发域内，夹带一项声明「不管」的事项——纯域外请求测的是裸模型，什么也证明不了
- 触发层要测双向：该触发时触发、**不该触发时不触发**（OpenAI skill eval 指南）

**效果。** 红线写法实验闭环：frontmatter 只写 "Not for" 的全灭，正文行为指令的守住；把「不管全文翻译」从 description 挪进正文红线节，同一用例 66.7% FAIL → 100% PASS。eval 不是打分，是改 skill 的扳手。

**失败模式。** 用经典任务测 skill（delta +0.00 然后误读为「skill 没用」）；用例资格没经过实测（先跑出 FAIL，它才配进套件）。

# 第 5 站：判定——三层评分器

**为什么。** 判定是假通过和假失败的主战场，单一评分器覆盖不了。结构分层 + 语义判定 + 因果对照，各抓各的虫。

**做什么。**

- **确定性断言**（便宜、可信、守 CI）：分三层——覆盖断言 FAIL 级（能力必须被真实调用，read_image 不许被 bash 兜底）、路径偏离 WARN 级（`must_call / must_not_call / max_tool_calls`，不断精确序列）、结果对错交终态判定（state_check 思想：查环境终态，不只看答复文本）
- **judge**（贵、守 preview/prod）：上岗先校准——TPR/TNR **分开看**（90% PASS 样本上一个橡皮图章也能拿 90% agreement）；给 Unknown 退路，unknown 占比反查 rubric；一个维度一个 judge；JSON Schema 机械强制「先依据后判定」（防先给答案再编理由）；pairwise 交换顺序跑两遍；校准集 fail 样本要够且**用有机失败不合成**（强模型合成缺陷是 OOD 反模式）；校准/验证集分开；人人一致靠「1 个独裁者好过 10 个民主者」（美团）
- **因果对照**：with/without 测增量，裸基线测「插件在场时宿主原有行为不变」——全绿也是结论，但没有裸基线，「全绿」和「没测到」长得一模一样

**假通过目录（八种）**：兜底答对 / 工具报错被粉饰 / eval 系统自身盲区（非零退出不许 PASS、筛选无命中报错）/ 提前宣告胜利（特性清单全初始化 failing）/ 局部验证 ≠ 端到端 / 终态 ≠ 对话记录 / 触发层假通过 / 预算内假通过（35 次调用解决的「不是 pass 是成本事故」）。
**假失败目录**：infra 错误被标成推理错误（修一个基础设施 bug 分数 50%→73% 的案例）；运行状态显式区分 completed/error/timeout，判定前先问「这次失败真的是 agent 的失败吗」。

**效果。** judge 格式从「首行判定」改成「先分析末判定」，消除格式诱导；长度上限等确定性红线全部可断言。

**失败模式。** 只看总一致率；拿人类一致性给 judge 放行（Kappa 的 prevalence 悖论）；对照组靠默认值。

# 第 6 站：统计——把观测变成数字

**为什么。** 点估计会骗人。单次跑分不作数（同一条用例三轮 25%/75%/100%）；小样本的「过线」没有统计意义（TPR=0.9、n=10 时置信区间宽到 0.55–1.0）。

**做什么。**

- **遮羞布和尺子分开**：失败重跑（治理偶发，让门禁不被抖动打红）vs trials 模式（跑满 n 次独立尝试，报单次成功率、pass@k、pass^k）——测量和门禁合体要是显式选择（`min_trial_success_rate`，判 Wilson 下界不判点估计）
- pass@k 的**估计**用无偏组合估计 1−C(n−c,k)/C(n,k)（n=k 套理论公式有偏）；pass^k 用 C(c,k)/C(n,k) 而非 plug-in（x^k 上凸，Jensen 保证向上偏）
- 两个数讲相反的故事：单次 0.75 的用例，pass@10≈1.0（看着完美），pass^10≈0.056（几乎必挂）——选哪个取决于你怕哪种错
- 门禁判**单侧 Wilson 上置信界**（z=1.645），不判对称区间更不判点估计；标准误随 √n 下降，误差减半样本翻四倍
- 分层聚合：聚合 pass rate 会把逐模型/逐后端的退化平均掉（70%→80% 的「正收益」里藏着至少一个模型的退化）
- i.i.d. 假设显式声明：限流、网络、模型状态漂移都破坏它；infra noise 实测能差 6 个百分点、比榜首模型分差还大（Anthropic）——榜单 3 个点以内的差距保持怀疑

**效果。** flaky 用例有专属标记而非混进 PASS；「10 次过 9 次」的用例过不过门禁有明确数学答案（下界 0.65，小样本不配谈达标）。

**失败模式。** 只报点估计不带 n；拿调过评分标准的同一批数据做最终验证；跨机器/时段比分数不带环境口径。

# 第 7 站：门禁——把数字变成决策

**为什么。** 没有门禁的指标是安慰剂；每个行为都要有数字，每个数字都要有门禁，否则「质量」只是形容词。

**做什么。**

- 判定是带退出码的协议（PASS=0/FAIL=1/N/A=2/WARN=0 或 strict 2），人和 CI 各取所需（文本行 + JSON 双形态）
- 基准报告入库是长期数据资产：schemaVersion、旧版补默认值、未知版本拒比较、重复用例名/非法状态一律拒跑——不让一份坏报告产出看似合法的判定
- 软→硬有量化晋升门槛（连续 5 次 PR 无 FAIL、误报 WARN ≤20% 才升级）——不是「感觉稳定了」，是「数据证明稳定了」
- 成本分层：便宜评分器守 CI（毫秒级），贵 judge 守 preview/prod
- 版本留痕：dshVersion 进报告，版本变化触发重校的纪律

**效果。** 全链路退出码让 CI 可判；「模型升级即触发全量重校」有基建在位。

**失败模式。** 门禁只看聚合数；WARN 和 N/A 混在同一个退出码里还指望 CI 分辨；报告格式无版本。

# 第 8 站（横切）：故障注入——主动制造失败

**为什么。** 等真实故障施舍，测不出检出能力。真实模型不会配合你确定性犯病——**协议故障必须 mock**（和 L4 行为语义必须真实链路，是同一条原则的两面）。

**做什么。**

- mock 三层：协议端点（按真实 API 方言手写事件序列）/ 故障即参数（六种故障 F0–F5 是请求参数，once + match/avoid 语义内建于故障源——外部协调复位永远比赛态窗口宽）/ **送达证明**（逐请求记录实际字节数、事件序列、终止证人——「工具没反应」和「故障没送达」必须分得开）
- **阳性对照细到协议事件名**：F5 think-only 必然触发 kimi 底层重试，测不出反应说明注入链路坏了；每个刺眼的阴性结论发布前当嫌疑人审——最刺眼的那个往往是自己的（mock 方言说错制造假阴性：`response.completed` 裹 status ≠ 独立事件 `response.incomplete`）
- 文件故障：截主文件/删附件/截附件/清 frontmatter，配机械证人（确定性检查器）与 agent 警觉性**分层记录**，阴性对照必带
- 故障可以造，**协议不变量不能破**（done 事件与 delta 拼接必须严格一致，否则触发的是另一条错误路径）

**效果。** 108 格矩阵：检出（L2+）只有 6/30，L0 占 60%，L2 整个空着——「检出不难，告知才是缺口」；skill 故障注入给出「检出率由伤的位置决定」（挡路 8/8，不挡路 2/8）；「带伤考官改不准带伤卷子」沿文档→理解→用例静默传导。

**失败模式。** mock 方言靠直觉拼；strings 阴性当「代码不存在」（Rust match 内联成立即数，不进 rodata）；把编排插件的辅助请求误判成重试。

# 第 9 站（横切）：评测系统自身的评测

**为什么。** 系列的全部翻案都指向同一件事：**裁判本身也要被校准**。观测会骗人（mtime 真的、数字一致的、结论错的）、考题会骗人（方言伪影）、对照组会骗人（老 profile 当对照，真凶是宿主新 profile 首启挂起）、绿灯会骗人（CI 构建的是合并态，本地是分支裸态）。

**做什么。**

- 判活器自身带回归测试（32 条断言 + 故意的坏样本）；排除计数（分母里少了谁必须显式）；单 case 重跑绝对路径纪律
- 误报原样保留（v1 错误归因 + 推翻过程，不改成「一开始就判对」）；公开更正的成本是一次尴尬，收益是可信的轨迹
- 用自己的协议改协议，再交外部 agent 评审——被抓出「两条规则字面矛盾」「执行端有义务、验收端无卡口」两个 Major：**规则写进 prompt 只是声明，得有人真的去查**

**效果。** 判活器上线抓到自己崩溃、配置漂移两个真 bug；harness 的超时杀不掉孙进程、runner 挂 34 分钟——评测工具被它要测的场景打穿，进程组杀修复。

**失败模式。** 只测被测对象不测裁判；错误结论悄悄改掉。

# 第 10 站：时间维——校准、漂移与套件治理

**为什么。** 单次跑绿只是开始。标准会漂、模型会换、用例会老、业务会变。

**做什么。**

- **标准漂移**（criteria drift）：人需要标准才能打分，打分又帮助人定义标准——评估标准无法在看到输出前完全定义，校准集有保质期，重校不是可选项
- **模型漂移**：干预有效性随模型版本衰减（Boris Cherny 每次换模型删掉 claude.md 再一点点加回来）；版本变化 → 触发重校
- **套件生命周期**：能力 eval（低通过率起步，爬坡）与回归 eval（接近 100%，守成）分两个套件；爬到顶的任务「毕业」进回归；100% 通过率是警报不是喜讯（eval saturation）；不再暴露新失败的用例定期剪掉——更多用例 ≠ 更好
- **业务分层**（企业视角）：模型能力指标 ≠ 业务结果指标，中间要一层桥梁指标（DAU/留存 ↔ 召回/点击 ↔ 意图/检索/整合），门禁绿了业务为什么还变差，个人项目框架回答不了——这是个人工程和企业的真实坐标差

**效果。** 门禁晋升门槛是套件治理的镜像（用例也有生命周期）；`dshVersion` 留痕让「版本→重校」有抓手。

**失败模式。** 校准一次管永远；用例只增不减制造进步假象；评测目标随业务扩量漂移却没人拍板（20 个指标一年变 200 个，得有独裁者）。

# 三条贯穿主线

1. **门禁是反馈回路，不是判官。** trace 提供观测，eval 提供误差度量，gate 把误差框在可接受范围内；判官追求一次判对，回路追求永远不跑偏太远——「不是单次运行的最优表现，而是长期不崩溃、不跑偏」（钱学森，《工程控制论》）。
2. **检出靠排除，不靠默认。** complete 是前面全部排除后才轮到的兜底档；「没证据说坏了」≠「证据说没坏」；阴性结论必须配阳性证据（送达证明、阳性对照、在场证明）。
3. **归因靠对照组，不靠证据强度。** 证据再硬也同时兼容两个相反的故事（modlens 归因推翻）；对照组选错比没有对照组更危险——它给你的错误结论配上了证据。
