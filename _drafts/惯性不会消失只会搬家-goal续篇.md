写完前几篇，我一度想用一句话概括这些失效：**惯性不会消失，只会搬家。** 模型层“把当前任务做完”的驱动被闸门按住以后，又会搬进连续性规则、验收标准和冻结目标里。

这个句子很漂亮。继续往下拆，我发现它不够准确：三个案例并不是同一种惯性，解决方案也不相同。把它们硬塞进一个词，反而会抹掉真正重要的差异。

它们共享的问题更接近**失联**：目标看不见当前工作，工作接不上验收，验收结果又推不动目标和任务状态。协议层因此有两条不能互相替代的轴：**执行是否不可绕过，语义是否接通。** 前一轴决定约束能不能生效，后一轴决定它有没有作用在正确的对象和时机上。这里说的“接线”不只是信息传递，也包括 authority：谁能写、谁能批准、谁能改变判定成功的标准。

## 一、先分开两件事：绕得过，与看不见

在结果导向的训练和评测里，“完成”常常与奖励直接相连。如果验收本身有漏洞，换窄目标、删测试、放宽断言，也可能被记成成功。我把这类倾向称为**完成压力**：它不是所有模型共有的单一机制，强弱也不能脱离具体模型、训练管线和任务环境来谈。

行为层面的证据确实存在。SWE-Marathon 实测 13.8% 的 rollout 出现 reward hacking；METR 2026 年报告里，最难任务约 16% 的“成功”因作弊被取消资格。这些数字说明绕过目标与验收的行为会发生，但不能单独证明它在每种模型里的成因，更不能推出一个通用的发生比例。

提示词里的“不许用更窄的方案替代目标”，约束的是模型当轮的决策；它不能替运行时封住替代路径。把高风险动作的裁决移到执行路径上，解决的正是这个问题：**模型不能仅凭一段输出让动作生效，放行权在模型之外。**

不过，硬闸门也不只是把规则从 prompt 搬进另一份文件。它至少要求所有高风险能力都经过不可绕过的裁决路径，并处理好失败时的默认行为、事务时序和并发竞争。否则，正门再硬，旁路仍然开着。

更重要的是，**不可绕过只解决“挡不挡得住”，不解决“挡的方向对不对”**。接下来三个案例，说的都是后一件事。

## 二、三个案例，其实是三种断线

### 1. 连续性保护接上了局部工作，却可能断开全局方向

LoopX 的交付连续性（delivery continuity）做了一件很合理的事：同一任务已有实质进展、仍可执行、归属有效时，后续心跳直接继续它，不必每轮拽回顶层重新判断。

这不是模型完成惯性原样搬进了协议，而是刻意调整决策节奏：顶层目标不必每次都干预局部执行，局部工作也不必反复证明自己为什么值得继续。它解决了冻结目标频繁“压顶”的问题，代价是渐进型漂移的通道随之变宽——每一步局部判断都说得通，整体方向却可能慢慢偏离，而且没有单个节点会报警。

LoopX 里并非没有纠偏机制。succession advisory 会把接续问题摆回人面前，replan 契约要求说清保留、改变和停止什么；但 `goal-direction-baseline` RFC 仍是“已接受、Partial”，M1 候选也不代表通用运行时已经启用。准确的说法不是“不跑偏还在图纸上”，而是：**已有对账与人工决策入口，通用的自动方向基线尚未完成。**

我会给这条连续性补上三份上下文：续跑所依据的 goal revision、当前 todo、已接受的进度证据；方向性 replan 再过 operator gate。局部工作值得保护，但保护不该意味着它可以脱离方向独自续跑。

### 2. 验收可以确定性执行，也可能确定性地判错

LoopX 的 owner 预声明验收把执行过程做得很硬：命令哈希 pin、快照执行，不接受调用方口头报告 pass/fail。它防止的是模型自己宣布成功，不能保证验收条件本身正确。

apex-law433 是一个现成反例：validate 只查 schema、不查内容，验收通过，任务仍然错误。这个例子能证明的是**验收配置质量会决定结果**；它不能证明验收之所以写松，是因为执行者的完成压力。后一种解释属于激励结构问题，需要单独的对照实验，不能从这个案例顺手推出来。

这里真正需要拆开的是验收标准的权限生命周期：**提议、批准、批准后修改、执行验收**，是四个不同动作。执行 agent 可以参与起草，但不能单方面批准判定自己成功的标准，也不能在批准后静默修改。批准后的版本要固定来源、哈希和适用范围；后续变更重新过 gate。

所以，“验收标准对执行 agent 不可写”还不够精确。更准确的防线是：**执行者不能独占地定义、批准和改变自己能否通过。** 来源分级有帮助，但它只是这套权限设计的一部分。

### 3. 冻结目标接上了历史约束，却可能断开任务演进

metacodes 的问题来自另一头。它的 goal 是一个扁平字符串、一个状态和一个账本；续跑时重新注入目标原文，AgentCore 路径还会把续跑提示作为持久 user 消息写进会话。旧副本可以被压缩，最新副本却始终在场。

百轮尺度上，这是防止遗忘和模型擅自改目标的好设计。千轮尺度上，工作已经进入子系统，目标却没有 revision 和历史，也无法表达任务图里的进展。旧约束没有消失，反而每轮被重新激活。问题不是“惯性反转”，而是**旧权威没有和新状态对账**。

TinyKG 任务 DAG 提供了改变注入结构的方案：每轮只给当前任务和根到当前节点的路径摘要。但 DAG 本身不是答案。若 goal 仍不知道任务图，验收仍不驱动节点和 goal 的状态迁移，父目标变更后也没有子树失效与对账规则，那么它只是把“每轮重注原文”换成“每轮重注摘要”。摘要还会带来自己的约束丢失问题。

三个案例摆在这里，已经很难再用一种“搬家”解释到底。它们分别需要方向对账、权限分离和版本接线。**看起来都是长程跑偏，断掉的却不是同一根线。**

## 三、真正要接的三根线

前面反复出现的，其实是三组协议关系。

**goal → 任务图：分解由谁起草，变更怎样传播。** 模型可以提议执行层节点，但目标与验收的权威来源必须说清楚。父目标变化后，哪些子任务继续、哪些重审、哪些作废，不能靠下一轮模型自行猜测。

**任务图 → 验收：节点完成由谁裁决，依据什么证据。** 验收条件要有来源和版本，执行结果要绑定到具体节点。把 verdict 写进图里只是记录，不是闭环。

**验收 → goal：验收结果怎样推动状态迁移。** 通过以后谁完成节点，失败以后进入重试、replan 还是 blocked，父目标变化时谁重新核实已完成的子树，都应该由协议明确，而不是靠模型记住几条提醒。

这些线也不能只存在于提示词里。至少要落到结构化状态、版本引用和状态迁移规则中：该拒绝的迁移会拒绝，该重新验收的节点不能沿用旧 verdict，该升级给人的决策不会被自动续跑吞掉。

这也是我现在对“协议层瓶颈”的理解：**不是把提示词写得更狠，也不是单纯把闸门造得更硬，而是让强制力和正确的状态接在一起。** 软而失联，模型可能绕开目标；硬而失联，系统可能把旧目标或错误验收执行到底。

## 四、多智能体增加的是交接面

多智能体不必然让系统更差，额外角色也可以提供交叉检查。但每多一个 agent、会话或宿主边界，目标和状态就多一次交接，也就多一处丢失语义、权限或账目的可能。

目标对齐因此不只是“每个 agent 都认真完成任务”。LoopX 用任务认领和归属约束同一件工作的责任方，检测到接续问题时不自动转移，而是要求显式决策。它接的是**归属与 authority**；至于各个局部工作合起来是否仍沿全局方向前进，还需要方向基线和证据对账。

状态传递也不只是消息有没有送到。LoopX 把跨轮、跨层交接拆成 Effect / Delivery / Authority 三级，并规定一次 scheduler tick 本身不能制造语义迁移。这里要防的是：状态格式正确、消息传递成功，执行权或历史含义却在交接中被悄悄改变。

预算则是一笔单独的账。Codex 把子线程用量沿 agent 树滚入 root 预算，接通的是成本归属，不是目标对齐；没有这条归集，子代理就可能成为主循环看不见的支出通道。

所以，多智能体实验不能只看最后完成了几个任务。等预算、多 trial、预注册指标仍然是底线；交接后的约束存活率、重复认领、孤儿节点、验收失效和总成本，也该进入观测。否则，多出来的 agent 到底提供了冗余校验，还是只增加了失联的位置，根本分不出来。

## 结尾

我现在不再用“惯性搬家”概括整件事。它能描述完成压力绕开软约束的那一半，却解释不了权限没有分离，也解释不了硬机制接着旧目标一路执行到底。

上一篇的结尾是：让证据代替信心，让验收独立于执行，让目标像代码一样被版本化和评审。再往下走一步，是把这些机制真正接起来：

**目标要知道自己在指导哪份工作，工作要用证据说明做到了什么，验收结果还要真的推动目标和任务状态改变。闸门要硬，线也要接上。** 否则，自动续跑只会把断线重复得更久。
