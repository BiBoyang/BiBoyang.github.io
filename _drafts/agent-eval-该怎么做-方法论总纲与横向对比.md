> 我把两年里给 agent 建质量基建的经验，和市面上二十来个评测项目放在一起对照了一遍。结论先说：大多数团队把 eval 等同于「跑 benchmark」，这是把体温计当成医生。benchmark 回答「它最好能做到什么」，门禁回答「它还是不是原来那个系统」。前者买外部可比性，后者买构念效度。这篇文章分三部分：我的方法论、市面上的项目怎么分类、以及从零开始该怎么建。

## 零、先把四个问题分开

「你们的 eval 做得怎么样」这个问题没法回答，因为它把四件不同的事压在同一个词上。

| 问题 | 你要的答案 | 判定对象 | 典型通过率 | 主要成本 |
|---|---|---|---|---|
| 能力上限 | 它能不能做到？ | 任务终态 | 20%–60%，越低越有信息 | 极高，样本要够 |
| 行为回归 | 它还是原来那个吗？ | trace + 终态 | 95%–100% | 低，可进 CI |
| 线上质量 | 真实用户遇到什么？ | 生产 trace + 业务指标 | 不适用 | 中，长期 |
| 供应链完整 | 它拿到的东西全不全？ | 文件/配置/协议 | 确定性 | 接近零 |

这四类问题的方法同源、目的不同，混在一起就会得出「SWE-bench 80 分，所以我们的 agent 可以发版了」这种结论。80 分是对「一组公开任务 + 某个脚手架」的测量，不是对你产品的测量，更不是对回归的测量。

我的全部经验可以压成一句话：**eval 不是打分，是建一条从 trace 到决策的反馈回路**。打分是回路里的一个环节，而且不是最容易坏的那个环节。

## 一、我的方法论：一条流水线，六条纪律

### 1.1 全景

```
问题层   能力上限      行为回归      线上质量      供应链完整
            │             │             │             │
数据层   trace：结构化事件 + 终态快照 + 成本账本 + 版本号
            │
实验层   用例 × 环境 × 对照组 × 钉版 × 在场证明
            │
判定层   终态  >  确定性结构  >  judge（校准后）
            │
统计层   n 次尝试 → 单次成功率 / pass@k / pass^k / 置信界
            │
决策层   门禁 / 发布 / 回滚 / 重校
```

这一整套东西，我在[「我的评测工具链」系列](/eval-series/)里用七篇事故报告拆开写过。这里不复述故事，只留骨架——每条纪律后面跟一句它为什么值得迁移到你的项目。

### 1.2 trace 是一等公民，第一天就要做

三类项目用三种姿势验证过同一件事：第一天就做的那个，793 个测试没有黑盒；晚两个月补票的那个，一批 provider 的 span 生命周期 bug 在「没有 trace 就看不见」的状态里活了两个月；把 trace 推到运行时本体那个，eval 反过来发现 trace 的字段缺口——恢复行为不可归因，于是补 `recovery_action`、`replan_count`。**trace 养 eval，eval 养 trace。**

好 trace 的标准只有五条：结构化且稳定的事件模型、格式带版本号、脱敏内建、能被测试断言、允许被 eval 反向塑造。这里有个容易混的角色区分：旁路遥测默认零开销、写入失败不许拖垮主流程；权威事件日志本身就是业务状态，写入失败必须 fail-fast。把两类都叫 trace，是很多设计事故的起点。

对 eval 的意义：**没有 trace，你只能断言 stdout**。有了 trace，断言对象从「输出了什么」变成「路径覆盖了什么、在哪一步失败、成本是多少」——这是 agent eval 和传统单测的分水岭。

### 1.3 实验先于断言：在场证明

我的 harness 曾有一个版本，dsh 子进程崩了（exit≠0）但 trace 断言全过，用例照样 PASS；另有一个筛选条件的笔误导致用例零命中，CI 空跑显示绿色。最狠的一次在 skill-up：九个 skill 全是符号链接，Go 的 `filepath.Walk` 不跟随符号链接根，一个文件没装进去，debug 日志照打 `skill installed`——三轮全量评测，with_skill 和 without_skill 跑的都是裸模型，报告里的 PASS 和 FAIL 全是 noise 装扮成的 signal。

所以第一条纪律不是「断言要写对」，是**全量跑之前，先验证被测对象真的在场**。不是看退出码，是看直接证据：工作区里的落盘文件、会话记录里「skill 被加载」的那行日志。PASS 只证明流程跑完了，不证明实验发生了。

### 1.4 对照组的纯度：宿主的默认值全是污染

with/without 不是展示，是因果推断。对照组和实验组之间唯一的差异必须是你注入的那个变量，其余一切都要钉死。现实是：

- kimi CLI 默认自动发现用户级 skills 目录，于是 without_skill 照样装进了九个 skill，「无 skill 对照组」名存实亡；
- 我自己配的 hook 每轮往上下文注「回复末尾附时间戳」，不仅污染被测 agent 的输入，还用 `⏱` 的 UTF-8 字节打碎了 judge 的 JSON 契约；
- 一个边界用例夹带了「写个 Python 脚本配 crontab 定时清理 /tmp」，`environment: none` 下 agent 真的照做了，在我的 crontab 里装了一条每天 00:17 的任务。

三条合起来是一条：**对照组的「无」必须被强制出来，隔离等级要按用例可能诱导的最坏行为来定，不是按用例的本意来定。**

### 1.5 双向归因：假通过和假失败

假通过我编过八种形态：agent 用 bash 兜底答对、工具报错被粉饰、eval 系统自身盲区、提前宣告胜利、局部验证冒充端到端、终态被对话记录冒充、触发层的假通过（该触发时触发、不该触发时也触发）、预算内的假通过（35 次工具调用换来的「成功」是成本事故）。

假失败这一面同样致命：评分器把超时和基础设施错误标成「推理错误」，就是在冤枉 agent。业内有现成的数字——修掉一个数据提取的基础设施 bug 后，基准分从 50% 跳到 73%。**判定前先问一句「这次失败真的是 agent 的失败吗」**，运行状态必须显式区分 completed / error / timeout。

一个经验：假通过比假失败更危险，因为它安静。假失败会有人喊冤，假通过不会。

### 1.6 judge 要校准，统计要判界

结构断言确定、可信、便宜；语义 judge 是另一个 LLM，它也会错，而且它的漏判直接变成门禁的假绿。校准纪律不复杂，难在坚持：

- **TPR 和 TNR 分开看**。样本里 90% 是 PASS 时，一个什么都放行的橡皮图章也能拿 90% agreement；
- **校准集要 fail 样本**，几百条里只有 5 条 fail 的集合没用；fail 不够就用弱模型产「有机失败」，让强模型合成缺陷是 OOD 反模式；
- **人类一致性不是 judge 的验收线**。人类 Kappa 常常只有 0.2–0.3，judge 到 0.4–0.6 就不错——但这不能给高风险 FAIL 的漏判率放行，安全、财务、发布阻断类该 95% 还是 95%；
- **一个维度一个 judge**，不给「God Evaluator」；
- **先分析后判定**，用 schema 强制 `checks[].notes` 必填，别让模型先给答案再编理由；
- **给 Unknown 退路**，unknown 占比高就先怀疑 rubric 不合格。

统计上只有一条核心：**判置信区间的界，不判点估计**。单次成功率 0.75 的用例，pass@10 约等于 1.0（看起来完美），pass^10 约等于 0.056（几乎必挂）——两个数讲相反的故事，选哪个取决于你怕哪种错。估计要用无偏组合估计：pass@k 是 `1−C(n−c,k)/C(n,k)`，pass^k 是 `C(c,k)/C(n,k)`，n=k 时套理论公式有偏。「10 次过 9 次」的点估计是 0.9，单侧 95% Wilson 下界只有约 0.65——小样本不配谈达标。

### 1.7 裁判也要被校准

这是系列里最反直觉、也最值钱的一条。七篇写下来，最后抓到的 bug 大多不在被测对象里，在测量系统自己身上：

- 我给 skill-up 报过一个不存在的 bug——mtime 数字全对，因为我 stat 的是旧 iteration；
- CI 红本地绿，我花一小时怀疑平台差异，真相是 GitHub 的 `pull_request` 构建的是「分支 ⊕ 最新 main」的合并态；
- 108 格矩阵里 codex 两格判 L0，发布前复核发现是我的 mock 把 `response.incomplete` 说成了 `response.completed` 裹一个 status 字段——**用法语考学生加法，差点判他不会算术**；
- 往二进制里 `strings` 搜事件名零命中，差点写成「代码不存在」——Rust 的 match 被内联成立即数比较，字符串根本不进 rodata。

对应的机制：判活器自测（32 条断言 + 故意的坏样本）、排除计数（`EXCLUDED: N case(s) without session-result`）、误报原样保留、阳性对照细到协议事件名。一句话：**工具链的价值不在永不出错，在错了之后能被抓回来。**

## 二、三条最可迁移的结论

上面是骨架。如果只让带三句话走，我选这三条——它们和主流 benchmark 的做法最不一样，也最容易被验证。

### 2.1 检出率由「伤的位置」决定，不由「伤的大小」决定

对 SKILL.md 做故障注入，批量口径的结果：

| 故障 | 与执行路径的关系 | 检出率 |
|---|---|---|
| 主文件截 60%（后续步骤消失） | 直接挡路 | 8/8 |
| 主文件截 85%（只丢尾部速查表） | 半挡 | 1/3 |
| 删掉指令点名要复制的模板 | 指令直接落空 | 3/3 |
| 参考文档截半（可选查阅） | 不挡 | 2/8 |

截掉 40% 检出 8/8，截掉 15% 反而 1/3。自变量从来不是「伤有多大」，是「伤是否横在 agent 正要执行的那条指令上」。

这条规律对做 eval 的人意味着：**故障注入要沿 agent 的执行路径设计，不要按故障严重度分层**。你在「下一步要用的那个文件」上做手脚，才会得到稳定信号；在「它可能根本不会读的文档」上做手脚，得到的 2/8 是骰子，不是测量。

### 2.2 内容层的完整性判不出来，必须下沉到供应链

108 格截断矩阵：30 个故障格里 L0 静默占 60%，L2（明确告知「回答被截断」）是 0，L3 那 6 格全是「重试 + 完整重放」。检出不难，告知才是缺口。skill 侧同理：截断的 SKILL.md 不产生错误码、不抛异常、validate 照过、报告照写。

三档防线的成本结构摆出来，结论就没得争：

| 防线位置 | 运行时 token 成本 | 可靠性 |
|---|---|---|
| skill 正文里的自检指令 | 每次加载都付 | 概率性（2/8 ~ 8/8 浮动） |
| CI / 发布期机械检查 | 零 | 确定性 |
| loader / 安装期校验 | 零 | 确定性 |

最贵的那档最不可靠。**完整性是供应链问题，不是上下文问题**——检查该长在 CI、loader、安装器上，不该写在提示词里让 agent 每次自己念一遍。

### 2.3 阴性结论必须配阳性证据

「工具没反应」和「故障没送达」是两件事，必须在证据上分开。我的 mock 每个请求落一条结构化日志：实际写出的字节数、完整事件序列、终止证人（`[DONE]` / `response.completed` / `message_stop`）送达没有。有了这层，翻案才有依据。

同理，F5（think-only 截断）是刻意的阳性对照：kimi 底层对空响应有现成重试，如果 F5 都测不出反应，说明注入链路坏了，所有「未检出」结论作废。

这条纪律迁移到 benchmark 上就是：**一个 benchmark 的低分，先要证明题目送到了、环境对了、评分器没 bug，否则低分不是能力信号**。Anthropic 给的 CORE-Bench 例子是现成的教材——评分器把 `96.12` 判成错、期望 `96.124991…`，一个 bug 就能把实际 95% 的模型压成 42%。

## 三、市面上的评测项目：五类，五种盲区

我不按「是不是 benchmark」分类，按**它回答哪个问题**分。

### 3.1 能力基准：回答「上限在哪」

这一类的共同点是 oracle 很强——真实测试、环境终态、可验证答案——所以分数可信度相对高；代价是贵、慢、容易被饱和和污染。

| 基准 | 领域 | 判定对象 | oracle | 备注 |
|---|---|---|---|---|
| [SWE-bench Verified](https://www.swebench.com/verified.html) | 仓库级修 bug | 测试通过 | fail-to-pass + pass-to-pass | 500 条人工验证；已从 30% 爬到 80%+，接近饱和 |
| [SWE-bench Pro](https://scale.com/blog/swe-bench-pro) | 长程软件工程 | 测试通过 | 同上，题目来自 copyleft/私有代码 | 1,865 条；GPT-5 23.3%、Opus 4.1 23.1%——不是模型退步，是题变难了 |
| [Terminal-Bench 2.0](https://www.tbench.ai/news/announcement-2-0) | 终端任务 | 容器终态 | 任务自带校验 | 容器化，配 [Harbor](https://harborframework.com/) 调度；人工 + LM 辅助验题 |
| [τ²-bench](https://arxiv.org/abs/2506.07982) | 对话式客服 | 环境终态 + 对话 | 数据库状态 + rubric | 双控（dual-control），用户由另一个 LLM 扮演 |
| [GAIA](https://arxiv.org/abs/2311.12983) / [Gaia2](https://huggingface.co/blog/gaia2) | 通用助理 | 最终答案/环境 | 可验证短答案、异步环境校验 | Gaia2 引入动态、异步环境，试图解决「静态题被背下来」 |
| [OSWorld](https://os-world.github.io/) / [WebArena](https://arxiv.org/abs/2307.13854) | 计算机/网页操作 | 环境终态 | 状态检查脚本 | 真 VM/浏览器，重且脆 |
| BFCL | 函数调用 | 调用正确性 | AST/执行比对 | 以函数调用为主，长程覆盖有限 |
| MLE-bench | ML 工程 | 提交分数 | Kaggle 评分 | 算力成本高 |
| CORE-Bench | 科研复现 | 复现结果 | 答案比对 | 对评分器 bug 极敏感 |
| BrowseComp | 深度检索 | 答案 | 可验证短答案 | 网络漂移是变量 |
| [HAL](https://proceedings.iclr.cc/paper_files/paper/2026/hash/a0928f924a344aaebbb7f6cd8d56e34c-Abstract-Conference.html) | 元基准 | 标准化 harness | 多基准统一接口 | 21,730 次 rollout、9 模型 × 9 基准、约 4 万美元、2.5B token |

HAL 值得单独说一句。它做的事不是又一个 benchmark，是**把「评测的基础设施」当成研究对象**：统一 harness、跨模型 × 脚手架 × 基准三维分析、把 2.5B token 的日志全部公开。它发现「提高 reasoning effort 在多数运行里反而降低准确率」，还用 LLM 辅助日志检查抓到 agent 去 HuggingFace 搜 benchmark 而不是解题。这两条都只能靠「有日志、能看过程」得到——纯分数永远看不见。

### 3.2 执行框架：解决「跑得动」

| 项目 | 定位 | 强项 | 盲区 |
|---|---|---|---|
| [Harbor](https://harborframework.com/) | 容器化 agent eval 基础设施 | 云上并行、registry、RL/SFT rollout 接口 | 不替你定义「什么算成功」 |
| [Inspect AI](https://inspect.aisi.org.uk/) | 通用 eval 框架（UK AISI） | dataset/solver/scorer 组合、200+ 现成基准、Docker/K8s/Modal 沙箱、能驱动 Claude Code/Codex/Gemini CLI 这类外部 agent | 它保证「评测能跑」，不保证「实验有效」 |
| [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness) | LLM 基准执行器 | 标准化、模型覆盖广 | 非 agentic，长程/工具场景不适用 |
| SWE-bench harness | 专用执行器 | 测试执行、容器隔离 | 只服务一个基准 |
| [skill-up](https://github.com/alibaba/skill-up) | skill 级评测 | with/without 对照、rule/script/judge 三层 | 内容层不校验；生态分母不透明 |

框架的共同价值是把「并发、沙箱、日志、评分器接口」这些重复劳动收掉。共同的风险是：**框架的 bug 会系统性地污染结论**。我自己的 harness 就交过卷——超时只杀直接子进程，包装器形态的孙进程被孤儿化，runner 挂了 34 分钟；skill-up 的零文件安装让三轮评测跑在裸模型上。选框架时，先问它「怎么证明实验真的发生了」，比问它支持多少模型有用。

### 3.3 平台：解决「看得见、管得住」

Braintrust、LangSmith、Langfuse、Arize Phoenix、DeepEval、promptfoo、AgentOps 这一层，能力组合大同小异：trace 采集 + 数据集管理 + 离线/在线评测 + 实验追踪 + 评分器库。

它们的强项是工作流：把「跑一次评测、看 trace、比两个版本」做成产品。盲区也一样整齐：

- 默认的 LLM judge 是**未校准**的，平台不会替你报 TPR/TNR；
- 落盘格式和关联键是**你的责任**，平台只负责展示；
- 「在线评测」很诱人，但线上信号的 ground truth 通常比离线更稀薄。

选型我只看三件事：trace 模型能不能导出（最好走 OpenTelemetry）、评分器能不能插自己的（而不是只能用它的）、成本口径能不能按用例切片。三件都行，剩下的就是价格和部署形态。

### 3.4 垂直/供应链：解决「东西全不全」

skill-up、skill-guard、skill-quake、插件生态评测都属于这一类。特点是 oracle 不在代码里，在 README 的承诺、规约的声明、宿主的不变量里。三个来源对应三种测法：README 承诺测「名不副实」，行为钉版测回归，宿主不变量测相容性。

这类评测最容易被忽略的是**分母**。dsh 插件生态里，一份清单收录约一千五百条、提个 YAML 就进；另一份较真的清单 9,247 个候选逐个真装，1,673 个实测，979 可用 / 600 不兼容 / 94 待定。**装得上的只有六成**——任何生态测评的结论，天然只对「可安装的头部」成立。把这个限定写进结论，比假装它不存在诚实得多。

### 3.5 标准与协议：解决「接得上」

[OpenTelemetry GenAI 语义约定](https://github.com/open-telemetry/semantic-conventions-genai) 定义了 model/agent/tool 的 span 形状，W3C `traceparent` 解决跨进程关联，MCP 统一工具接口。它们的价值是让 trace 可移植、可 join、可跨工具比较。

盲区也明确：**标准只定义字段，不定义「什么算成功」**。你可以有全世界最规范的 span，然后拿它去断言一个错误的成功标准。

### 3.6 一张对照表

| 类别 | 代表 | 回答的问题 | 判定对象 | oracle 强度 | 归类为 | 主要盲区 |
|---|---|---|---|---|---|---|
| 能力基准 | SWE-bench、Terminal-Bench、τ² | 上限在哪 | 终态 | 强 | 对外 | 饱和、污染、scaffold 混淆 |
| 执行框架 | Harbor、Inspect、lm-eval | 怎么跑起来 | 框架 | 不判定 | 基建 | 框架 bug 污染结论 |
| 平台 | Braintrust、LangSmith、Langfuse | 怎么看、怎么管 | trace + 数据集 | 弱到中 | 工作流 | judge 未校准、格式你负责 |
| 垂直供应链 | skill-up、skill-guard | 东西全不全 | 文件/配置 | 强（确定性） | 对内 | 分母、版本漂移 |
| 标准协议 | OTel GenAI、traceparent | 接不接得上 | 字段 | 不判定 | 基建 | 不定义成功 |

### 3.7 同一个问题，benchmark 和门禁的两种答法

把上面的分类压到一张表里，差异会更清楚。这不是「谁更好」，是「各自优化什么」。

| 维度 | benchmark 的做法 | 自建门禁的做法 |
|---|---|---|
| 用例从哪来 | 出题人设计，追求覆盖与难度 | 从自己的真实失败反推，追求相关性 |
| oracle | 官方测试、环境终态（强） | 终态 + 结构断言 + 校准过的 judge（混合） |
| 环境 | 固定镜像，追求一致 | 你的真实宿主，追求保真（但要隔离） |
| 统计口径 | 报 pass@1 / pass@k 点估计 | 判 Wilson 下界，报 n |
| 版本管理 | 基准版本（Verified、2.0） | agent 版本 + 报告 schemaVersion + 模型版本 |
| 失败归因 | 一个分数 | 故障域（规划/工具/环境/skill） |
| 更新节奏 | 年度新版，防饱和 | 每个修过的 bug 加一条，定期剪枝 |
| 激励 | 排名、对外证明 | 合并决策、防回归 |
| 单次成本 | 高（容器、长程、多 trial） | 低（可进每次 CI） |
| 主要风险 | 饱和、污染、scaffold 混淆 | 过拟合自己的 bug、样本太小 |

一句话：**benchmark 是别人替你写的用例，门禁是你替自己写的用例**。前者的强项是外部可比，后者的强项是构念效度。成熟的团队两个都跑，而且知道哪个数字能回答哪个问题。

## 四、benchmark 的六个结构性缺陷

这一节不是唱衰 benchmark。它们推动了整个领域，我的 harness 里一半的纪律是从 benchmark 社区学的。但把它们当发布门禁用，会踩六个坑。

### 4.1 饱和与污染

SWE-bench Verified 一年从 30% 爬到 80%+，接近饱和；SWE-bench Pro 换了一批模型没见过的代码（copyleft 的「传染性」让厂商倾向于排除，加上 Scale 的私有商业代码库），同样的前沿模型掉到 23%。**这不是模型退步，是题目终于开始测泛化了。**

饱和的副作用是「进步看起来变小」：只剩最难的题，大幅能力提升在分数上只体现为几个点。Anthropic 举的例子很典型——Qodo 一开始对 Opus 4.5 无感，因为他们的 one-shot coding eval 根本测不出长程任务的增益，换成 agentic eval 才看见。

### 4.2 scaffold 混淆：榜单测的是「模型 + 脚手架」

SWE-bench 主榜比的是任意 agent 系统，不是模型。官方为此专门做了一个 bash-only 的 `mini-SWE-agent` 对照，让所有模型在同一个最小脚手架上跑，才勉强算 apples-to-apples。即便这样，release 1.x 和 2.x 因为工具调用方式不同，分数也不可直接比。

对你的意义：**榜单分数和你的产品之间，隔着你的脚手架**。prompt 组装、工具协议、上下文管理、审批回调——每一项都能吃掉几个到几十个点。拿榜单分数做选型，等于拿别人的体检报告给自己开药。

### 4.3 评分器 bug：grader 是被测系统的一部分

CORE-Bench 那个例子值得抄在本子上：Opus 4.5 起初 42%，查下来是刚性判分（期望 `96.124991…` 却拒收 `96.12`）、任务描述含糊、随机任务不可精确复现；修完评分器和脚手架，95%。METR 也发现自己的一批任务「要求优化到阈值、判分却要求超过阈值」，结果**听话的模型被罚，忽略指令的模型得分更高**。

推论：一个 0% 的 pass@100，大概率是题目坏了，不是模型不行。Anthropic 的原话是——前沿模型上大范围零通过，通常是任务或评分器有问题的信号。反过来，一个 100% 的通过率是警报不是喜讯。

### 4.4 排行榜激励：分数不是能力的无偏估计

NeurIPS 2025 的《The Leaderboard Illusion》把 Chatbot Arena 的机制拆开：有厂商在公开发布前私下测了 27 个变体、挑最好的那个上榜，分数不理想还能撤回；前两名厂商各拿到约 19.2% 和 20.4% 的评测数据，而 83 个开源模型合计只有 29.7%；额外的 Arena 数据在 ArenaHard 上能带来最高 112% 的相对提升。

这不是某一家的问题，是**排行榜作为激励系统的结构问题**：可选择性披露 + 数据不对称 = 分数向「会玩这个游戏的人」倾斜。看榜时至少要知道：这个分数是谁跑的、跑了几个变体、脚手架公开没有、有没有撤回记录。

### 4.5 基础设施噪音：环境本身是变量

Anthropic 在 Terminal-Bench 2.0 上量化过：最严和最松的资源配置差 6 个百分点（p<0.01），比榜首模型之间的分差还大；通过率甚至随一天中的时段波动。他们给的消费纪律可以直接引用：**榜单上 3 个百分点以内的差距，在 eval 配置公开并对齐之前，保持怀疑。**

我的 harness 也踩过同构的坑：报告记了 `dshVersion`，没记机器、负载、时段。一旦要跨机器比分数，这个缺口就会咬人。

### 4.6 构念效度：benchmark 测的是「在 benchmark 上的表现」

这是六个里最深的一个，也是自建门禁存在的理由。

benchmark 的失败分布是**出题人选的**，你产品的失败分布是**你的用户选的**。两者交集多大，没人替你验证。Hamel Husain 和 Shreya Shankar 那套「先 error analysis 再写 rubric」的纲领，本质就是在补构念效度：评估器该为已发现的错误而建，不该为想象中的错误而建。

所以我不建议「用 benchmark 当门禁」，但我强烈建议「用 benchmark 当参照系」——它告诉你行业把「难」定义在哪，你的用例集有没有漏掉整个维度。

## 五、从零开始该怎么建

顺序很重要。大多数人从「选工具」开始，正确的顺序是从「错误的代价」开始。

### Step 0：先写清楚你要回答哪个问题

四选一，别混：

- 要对外证明能力 → 用现成 benchmark，把版本、脚手架、预算、采样次数一起公开；
- 要防回归 → 自建门禁，用例来自你自己的 bug；
- 要知道线上好不好 → 生产监控 + 定期采样人读，别指望离线集；
- 要保证供应链 → CI 静态检查，零 token，确定性。

几类都要，就建分层套件，不要指望一个套件通吃。

### Step 1（第一周）：trace + 20–50 条用例 + 20 条人工标注

- trace 先落盘：结构化事件、版本号、脱敏、稳定关联键；
- 用例从真实失败反推。上游的 fix 记录是最好的种子库——每修一个 bug，配一条红绿对照用例；
- 先看 20–30 条真实 trace 再写标准。标准不是想出来的，是标出来的；
- 标签用二元，不用 1–5 分。坚持要细粒度分「以便日后调阈值」的人，我见过真的调过的是零个；
- 20–50 条就够起步。Anthropic 的原话是越晚建越难，拖久了只能对着线上系统逆向工程成功标准。

### Step 2：oracle 分层，能用强的不用弱的

```
环境终态（数据库里有这条记录吗）
  > 真实副作用（外部系统状态变了吗）
    > 确定性结构（工具调用、事件序列、退出码）
      > 参考输出比对
        > rubric judge（校准过才算数）
          > 人类（金标，但慢）
```

三条硬规则：

1. **覆盖断言是 FAIL 级**：想测的能力必须被真实调用，read_image 不许被 bash 兜底；
2. **路径偏离是 WARN 级**：调了该调的，只是顺序/方式不同——记录，不否决。Anthropic 在 τ²-bench 上见过 Opus 发现政策漏洞给出更优解却被判 fail，那是惩罚超出设计者想象力的行为；
3. **结果对错交给终态**：agent 说「航班订好了」是对话记录，数据库里有没有预订是终态。

写不出可判定断言时，正确动作是标「不可判定」，不是写一条永远通过的橡皮图章。

### Step 3：实验有效性四件套

| 件 | 做法 | 反面教材 |
|---|---|---|
| 在场证明 | 落盘文件 + 会话日志行 | 符号链接零文件安装，三轮跑裸模型 |
| 对照纯度 | 强制隔离宿主 skills/hooks/env | without_skill 自动发现九个 skill |
| 隔离等级 | 按最坏行为定，默认容器 | crontab 被真的装了一条定时任务 |
| 钉版 | 版本、机器、预算、日期进报告 | 被测 CLI 被更新提示顶成新版 |

### Step 4：统计口径写进报告

- 每份报告带 n，不带 n 的比率是轶事；
- 重跑和尺子分家：失败重跑管 CI 绿不绿，trials 模式管你敢不敢信它；
- 判 Wilson 下界，不判点估计；
- 分层看：聚合 pass rate 70%→80% 的「正收益」里，可能藏着一个模型/后端的退化；
- i.i.d. 是假设不是事实，限流、网络、模型状态漂移都会破坏它——报告里显式声明。

### Step 5：门禁是带退出码的协议

- PASS=0 / FAIL=1 / N/A=2 / WARN=0（strict 下 2）；文本行 + JSON 双形态，人和 CI 各取所需；
- 报告带 schemaVersion，旧版补默认值，未知版本拒比较；重复用例名、非法状态一律拒跑；
- 软到硬有量化晋升门槛：连续 5 次 PR 无 FAIL、误报 WARN ≤20% 才升级——不是「感觉稳定了」，是「数据证明稳定了」；
- 成本分层：便宜的确定性评分器守 CI（毫秒级），贵的 judge 守 preview/prod。

### Step 6：meta-eval 一开始就埋

- 判活器自己要有回归测试，含一个故意的坏样本；
- 排除计数：分母里少了谁必须显式；
- 误报原样保留，推翻过程比结论值钱；
- 每个刺眼的阴性结论，发布前当嫌疑人审一遍——最刺眼的那个，往往是你自己的。

### Step 7：时间维——校准、漂移、套件治理

- 能力 eval 和回归 eval 分两个套件：前者低通过率起步，后者接近 100%；
- 爬到顶的能力任务「毕业」进回归套件；
- 不再暴露新失败的用例定期剪掉——更多用例 ≠ 更好；
- 标准漂移（criteria drift）是真实的：人需要标准才能打分，打分又帮助人定义标准，所以校准集有保质期；
- 模型升级即触发全量重校。干预的有效性随模型版本衰减——每次换模型都该重跑，而不是假设昨天的红线段今天还成立。

### Step 8：成本模型

| 层 | 单次成本量级 | 频率 | 用在哪 |
|---|---|---|---|
| 静态检查 | 0 | 每 commit | CI |
| 确定性断言 + 真实 agent | 约 1 万 token/条 | 每 PR | 门禁 |
| LLM judge | +1–3k token/条 | 每 PR 或 nightly | 语义层 |
| trials（n 次） | n × 上两行 | 每周 | 尺子 |
| 全量 benchmark | 美元到万美元级 | 换模型/季度 | 对外 |

我的 12 条用例全量约 12 万 token，deepseek-chat 量级下成本可以忽略；HAL 的 21,730 次 rollout 约 4 万美元。**贵不贵取决于你问的问题**，不取决于工具。

### 反模式清单

- 用 benchmark 分数当发布门禁；
- 用单次跑分下结论；
- 用总一致率验收 judge；
- 用聚合分数掩盖分层退化；
- 用例只增不减，制造进步假象；
- 用退出码证明实验发生；
- 用 mock 顶「行为语义」的岗（它只该顶「协议故障」的岗）；
- 用 judge 顶「终态」的岗；
- 用「没有报错」当「没有问题」。

## 六、我的方法的边界

写方法论最容易犯的错，是把自己的场景当成通用场景。这份清单是留给 review 的：

- **单轮**。所有用例都是单 session，LangChain 三原语里 thread 那一层（跨 session 的状态演化）我完全没覆盖；
- **judge 校准立了法，没带回数字**。TPR/TNR、拒答率、Wilson 界，系列里写了纪律，自己的套件上没有实测——这是最实的窟窿；
- **N 小**。宿主矩阵 N=8/3，只能分「稳定/概率性/稳定漏检」三档，x/N 不该被读作比率估计；
- **变量混杂**。Claude Code 那一列实际跑在 DeepSeek v4.1 flash 上，宿主脚手架和模型两个变量同时变了，检出差异不做归因拆分；
- **无业务桥梁指标**。门禁绿了、业务为什么还变差，我的四层模型（日志→归因→评测→决策）回答不了。美团那套「模型能力指标 ↔ 任务系统指标 ↔ 业务结果指标」的搭桥，是企业场景才有的第三层；
- **标准由一个人定**。个人尺度成立（「1 个独裁者好过 10 个民主者」在团队里同样需要那个独裁者），但「谁的标准」在团队里本身就是第一道题；
- **真实重跑 vs 回放**。我选全真实重跑，保住了并发与时序；代价是贵、抖、低概率竞态可能样本内不触发。回放冻结工具观测，TOCTOU 在回放里物理上不存在——两种范式盲区互补，不是谁更先进。

## 七、收尾：四个时间尺度

评测这件事，最后是按时间尺度分工的：

- **毫秒级**：确定性断言，每次提交都跑，守 CI；
- **分钟级**：一次完整 agent session，每个 PR 跑，守行为；
- **周/月级**：套件本身，校准、毕业、剪枝、重校，守方向；
- **季度级**：benchmark、业务指标、竞品对照，守战略。

四个尺度混用，就会出现「拿季度级的分数做每次提交的决策」或者「拿毫秒级的断言回答『我们的 agent 强不强』」——两者都是把体温计当医生。

所以回到开头那句话：benchmark 让你知道自己在人群里的位置，门禁让你知道自己有没有走丢。前者一年看几次，后者每次提交都看。**把两者混为一谈的团队，通常会得到一个很漂亮的分数和一个很脆的系统。**

如果只能记一句，记这句：门禁不是判官，是反馈回路。回路里的每一环——trace、考题、对照组、观测者、judge——自己也会坏，所以裁判本身也要被校准。判官追求一次判对，回路追求永远不跑偏太远。

## 附：一页纸检查清单

**建之前**

- [ ] 我回答的是四个问题里的哪一个？
- [ ] 失败样本从哪来？有没有先看 20 条真实 trace？
- [ ] 这个用例的「通过」能被环境终态验证吗？不能的话，我标「不可判定」了吗？

**每次跑**

- [ ] 被测对象在场吗？证据是文件/日志，还是退出码？
- [ ] 对照组和实验组只差一个变量吗？宿主的 skills/hooks/env 钉死了吗？
- [ ] 隔离等级是按最坏行为定的吗？
- [ ] 版本、机器、预算、日期进报告了吗？

**判定**

- [ ] 覆盖断言 FAIL、路径偏离 WARN、结果看终态，分开了吗？
- [ ] judge 校准过吗？TPR/TNR 分开了吗？校准集和验证集分开了吗？
- [ ] 失败是 agent 的失败，还是 infra 的失败？

**统计与门禁**

- [ ] 报告带 n 吗？判的是界还是点？
- [ ] 分层看了吗？
- [ ] 门禁有退出码协议和 schemaVersion 吗？
- [ ] 连续绿了几次才允许升级为硬门禁？

**长期**

- [ ] 判活器自己有测试吗？排除计数有吗？
- [ ] 上一次全量重校是什么时候？换模型之后重校了吗？
